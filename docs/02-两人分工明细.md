## 0. 分工原则

原说明第 7 节列了 **4 个角色**（数据/工程、策略/统计、报告/文档、宣发/合规），但**只有 2 个人**。合并规则如下：

| 原角色 | 归谁 | 理由 |
|---|---|---|
| 数据/工程 | **A** | 硬技能壁垒（采样器 + 成本模型 + 数据管线），不可拆分 |
| 策略/统计 | **B** | 需独立于工程实现做假设检验，避免"自己写自己验" |
| 报告/文档 | **B 主，A 供料** | B 掌握统计结论口径；A 只提供数据/成本章节素材 |
| 宣发/合规 | **A 主，B 复核** | 与仓库工作同源，属"非分析型"任务 |

### 三条铁律

1. **每个交付物有且只有一个 DRI**，另一人角色是**复核者**，不是"共同负责"。
2. **样本外只有 B 能执行，A 不得代跑**——B 是参数冻结的签字人，跑 OOS 的必须是签字人本人。
3. **接口先于实现**：A 与 B 靠 §3 接口契约通信；契约冻结后各自写码，**不互相等**。

## 3. 接口契约（A → B）· **9/12 晚冻结，之后各自写码**

### 3.1 文件约定

| 文件 | 生成者 | 消费者 | 内容 |
|---|---|---|---|
| `data/spread/YYYY-MM-DD.csv` | A | B | `ts_utc, symbol, bid, ask, mid, spread_bp, bidSz, askSz` |
| `data/raw/{symbol}_1m.json` | A | B | Bitget `candles` `granularity=1min`（**有缺口，勿当连续序列**） |
| `data/raw/{symbol}_1h.json` | A | B | Bitget `candles` `granularity=1h` |
| `data/raw/{ticker}_1d.json` | A | B | Yahoo `chart`，原生股日线 |
| `data/panel.parquet` | A | B | 对齐面板：`ts_utc, symbol, P_rtoken, P_official_close, dev_bp, session, spread_bp` |
| `costs.json` | A | B | 分时段/分标的费率与点差（悲观/中性/乐观三档） |
| `universe.csv` | A | B | 标的筛选结果 + 入选/排除理由 |

### 3.2 字段级约定（**最容易出错的地方**）

| 字段 | 单位 | 口径 | 备注 |
|---|---|---|---|
| `ts_utc` | 毫秒或 ISO8601 | **一律 UTC** | 展示层再转 ET/CST；ET 用 `zoneinfo` |
| `dev_bp` | **bps**（不是 %） | `(P_rtoken / P_official_close − 1) × 10000` | — |
| `P_official_close` | USDT/股 | **最近一次已收盘**的官方收盘价 | **禁止用到未来收盘**（N4 前视） |
| `spread_bp` | bps | `(ask − bid) / mid × 10000`，**全幅** | maker/taker 各取**半幅**，符号相反 |
| `session` | 枚举 | `{intraday, afterhours, overnight, premarket, weekend, holiday}` | **单一实现** `session.py` |
| `cost_bp` | bps | **三项分开** | `{fee_bp, half_spread_bp, slip_bp}` + `liquidity_role` |

| 复核规则 | 复核者**必须真的跑一遍**，不接受"看起来没问题"（尤其 N1 与 G4） |
| 冲突裁决 | "是否降复杂度/是否放弃某功能" → **B 定**（守 G1–G5）；工程可行性 → **A 定** |

---

## 6. "完成"的定义（DoD）

一件任务只有**四条全满足**才算完成：

1. 产物已落盘到**约定路径**（不在聊天记录里）；
2. **一条命令可复跑**（写进 README 或当天同步消息）；
3. **对方复核通过**（复核者亲手跑过）；
4. 若涉及门禁，**对应 Gx 已显式标记通过/不通过**（不允许"大概没问题"）。
