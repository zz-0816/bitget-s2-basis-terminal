## 问题 1 · 做市策略是否匹配目标人群（小金额人群）？

### 1.1 先给硬结论

**「做市」作为用户的赚钱方式，不匹配主用户。**
**但「做市作为执行方式」恰恰直击主用户的痛点。**

这两句话是本项目最需要分清的边界，写错方向会在表单第 2 段（目标用户）失分。

### 1.2 为什么"做市赚钱"不匹配主用户

| 维度 | 主用户（亚欧美股散户） | 做市策略要求 | 匹配？ |
|---|---|---|---|
| 资金规模（次用户 1k–100k USDT） | 1,000–100,000 USDT | 实测顶部单侧深度 $1k–$2M → **资金不是瓶颈** | ✅ 容量够 |
| **能否做 maker** | 会看盘、懂技术指标，**不一定会挂单套利** | 必须持续挂单 + 撤单 + 双场所同时管理 | ❌ **能力不匹配** |
| **最重要的事** | 想要美股敞口、想抓周末行情 | 做市赚的是**点差**，不是方向 | ❌ **诉求不匹配** |
| 时间投入 | 晚上看一眼盘 | 做市需盯盘/跑程序 | ❌ 不现实 |
| 可解释性 | 要"看得懂" | 做市收益来自微观结构，难懂 | ❌ |

**一句话**：主用户要的是"**在休市时能买到美股**"，不是"**给市场提供流动性赚点差**"。把做市当卖点卖给散户，是答错了题。

### 1.3 但这里有个真正匹配的切入点

我们实测出的最硬事实是：**休市时段现货点差 3.31–45.63 bp（中位约 13 bp），盘中则塌缩（TSLA 实测 31.79 → 2.19 bp，−93%）。**

对散户来说，这意味着：
> **在休市时段用市价单进出，每次先亏掉 0.03%–0.46%。** 而这正是散户最常干的事（"周末看到新闻，直接市价买入"）。

**所以正确的产品定位是**：
> 给主用户的**执行感知层（execution-awareness）**：告诉他"现在点差有多宽、该用限价而不是市价、该等哪个时段"——
> **从"付点差的人"变成"不付点差（甚至赚点差）的人"。**

这不是新功能，**它就是我们做市研究的自然产出**：我们为了做市必须量化点差与深度，而这份量化结果**本身就是散户最需要的工具**。

### 1.4 两个项目分别对准两类用户（正好契合手册的"两投"）

| | **项目一（首选）** | **项目二（次选）** |
|---|---|---|
| 子主题 | ①「套利」 | 开放主题（Execution-aware Alpha） |
| 核心 | 跨场所基差做市 | **点差/成本感知的执行层** |
| **目标用户** | **次用户**：1k–100k USDT、会 Python、已在多平台有仓位的小型量化散户 | **主用户**：亚欧美股散户，休市时段想动手但被点差吃亏 |
| 用户价值 | 赚基差 + 点差 | **知道什么时候不该市价买、省下多少** |
| 手册第 2 段怎么写 | 写"小型套利/量化散户"（具体人群，非"所有 trader"） | 写本文 §1.1/§1.3 的散户画像 |

> **这样就同时解决了两个问题**：① 做市策略有了对口的用户（次用户）；② 主用户的痛点（点差黑洞）由一个独立项目承接。
> 而且**两个项目共用同一套数据与成本模型**，2 人 9 天的边际成本可控。

### 1.5 必须写进报告的一句话

> 本策略的目标用户是**已在 Bitget 持有 USDT、同时接触 rToken 现货与美股合约的小型量化散户（1,000–100,000 USDT）**，
> 而非泛散户群体。泛散户由配套的"执行成本感知"工具服务——该工具告诉他们**休市时段市价单的真实代价**，
> 并引导其改用限价单。**我们不做"稳赚"承诺**；本策略承担方向与逆向选择风险，属做市型价差捕获，**非无风险套利**。

## 问题 2 · 分钟级数据的累积条件与关机恢复

### 2.1 两条数据线的本质区别（**这是关键**）

| | **K 线**（`/candles`） | **盘口快照**（`/tickers`） |
|---|---|---|
| 谁产生的 | **交易所** | **我们自己轮询抓的** |
| 交易所是否留存 | ✅ 留存 | ❌ **不留存**（只有"此刻"的 bid/ask） |
| 关机后能否补回 | ✅ **能**（翻页 `endTime`） | ❌ **永久丢失** |
| 覆盖内容 | 开高低收 + 成交量 | **点差、盘口深度、基差**（策略的核心变量） |

> **残酷但必须认清的一点**：
> 我们最需要的两个变量——**点差**和**盘口深度**——只存在于"我们抓的那一刻"。
> **Bitget 不提供 bid/ask 的历史接口**，所以关机期间的点差/深度**任何平台都补不回来**。

### 2.2 直接回答你的问题

> **问**：逐步累积的分钟级 K 线，监控的条件是什么？关机后下次启动会不会补全关机时的 K 线？

**答**（分两半）：

**（a）K 线部分：会补全，且我们已有工具。**
- 现货 1min 回溯约 10 天（2026-09-02 起），永续 1m 同样约 10 天
- 命令：`python backfill_history.py --gran 1min --days 10`
- 幂等：按 `ts_ms` 去重合并，重复运行只补新增，不会写重
- **限制**：只能补到平台保留上限（约 10 天）。**关机超过 10 天，那部分 K 线也补不回来了。**

**（b）盘口快照部分：不会补全，永久丢失。**
- 关机期间的 `spread_bp` / `bid_depth_usd` / `ask_depth_usd` 无法恢复
- **但基差仍可事后由 K 线重算**（基差 = 现货收盘 / 永续收盘），所以**损失的是"点差/深度"这一层，不是全部**

### 2.3 监控条件（采样器实际依赖什么）

| 条件 | 说明 |
|---|---|
| ① 进程存活 | 两个采样器各自单实例锁；退出时释放锁 |
| ② 出网可达 | 直连 `api.bitget.com`；实测 Python `urllib` 可用（**不要用 `curl.exe`**，有 schannel bug） |
| ③ 电脑不休眠/不关机 | **这是唯一无法用软件绕过的条件** |
| ④ 磁盘可写 | `data/spread/` 追加写，按 UTC+8 日期分区 |

### 2.4 已交付的"看门"工具：`tools/data_integrity.py`

它把"关机丢了多少"**量化出来**，而不是靠感觉。实测输出示例：

```
【1】自采盘口快照（不可回补）
  2026-09-12.csv   轮次 71   覆盖 13:01 → 14:11
                   期望约 71 分钟 / 实得 71 分钟 → 覆盖率 99.7%
                   无 >5 分钟空洞
【2】全池轮转采样
  universe-2026-09-12.csv  行 1128  轮次 21  已覆盖标的 213
【3】K 线（可回补）
  1min  文件 20  最早 2026-09-02 09:52  最晚 2026-09-12 13:28
```

**它做三件事**：① 报告自采覆盖率的**空洞**（不可恢复损失）；② 报告 K 线可补范围；③ 明确标注两类数据的可恢复性差异。

**建议开机后固定执行一次**：
```powershell
python tools\data_integrity.py
python backfill_history.py --gran 1min --days 10      # 补 K 线
python backfill_history.py --gran 1h   --days 120
```

### 2.5 降低关机损失的三条措施（按性价比排序）

1. **让机器别睡**（性价比最高）：
   ```powershell
   powercfg /change standby-timeout-ac 0
   powercfg /change hibernate-timeout-ac 0
   powercfg /change monitor-timeout-ac 15
   ```
2. **接受"点差层"会有洞，并在报告里如实标注**（手册重视诚实方法论，隐瞒才是致命伤）。
3. **关机前手动导出一次**（可选）：把当日 CSV 归档到 `data/snapshots/`，至少保证已有数据不丢。

### 2.6 ⚠️ 一个必须记录的运维事实

今晚观察到一个现象：**采样器进程 PID 会变动**（`3956 → 2380 → 2324`，锁文件随之更新），说明存在**进程被重启/接管**的情况。
**已做的验证**：对两个采样 CSV 做了重复检测——

| 文件 | 行数 | 唯一 (ts, symbol, venue) | **重复** |
|---|---|---|---|
| `2026-09-12.csv` | 2,820 | 2,820 | **0** |
| `universe-2026-09-12.csv` | 1,128 | 1,128 | **0** |

→ **数据是干净的，没有多实例重复写入**。
→ 但仍需注意：**长期常驻建议在你自己的终端启动**（而非依赖会话内的后台作业），避免被会话生命周期影响。

### 第 1 层宽基回测数据已就绪（`build_panel.py`）

**1h 面板实测（10 配对 / 58 天 / 13,636 个对齐样本）**：

| 时段 | 样本 | 均值 bp | **中位 bp** | 最小 bp | 最大 bp |
|---|---|---|---|---|---|
| **休市** | 6,936 | −13.40 | **−12.46** | −286.28 | +297.60 |
| 盘前 | 2,514 | −11.57 | −11.21 | −83.59 | +130.34 |
| 盘中 | 2,514 | −10.62 | −10.33 | −57.95 | +34.98 |
| 盘后 | 1,672 | −10.36 | −9.76 | −81.27 | +89.86 |

**三条结论**：
1. **基差在所有时段方向一致为负** → 是**结构性**的，不是某天特例。这是策略成立的最重要前提。
2. **休市时段基差最负（−12.46 bp，比其他时段更极端）** → 与"休市窗口更值得交易"一致。
3. 按标的分：SOXL −14.16 / META −13.81 / HOOD −13.33 / MRVL −13.16 **最负**；NVDA −7.35 / SPY −9.37 较小。

**对齐口径已固化（防前视）**：以永续为时间轴（连续），为每个永续 bar 匹配**同时刻或之前最近**的现货 bar，滞后超过 3 个 bar 则记为缺测。实测滞后中位 0 bar、非零占比仅 6.8%。
