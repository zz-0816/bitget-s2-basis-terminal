## 4. 根因（两个，都已定位）

**① ISP 对 `bitget.com` 按 SNI 封锁。** 同一 Cloudflare IP 上换非 Bitget 的 SNI 完全正常：

    104.18.23.226 + SNI datahub.noxiaohao.com -> TLS OK (TLSv1.3)
    104.18.23.226 + SNI api.bitget.com        -> ConnectionReset
    104.18.14.166 + SNI datahub.noxiaohao.com -> TLS OK
    104.18.14.166 + SNI api.bitget.com        -> ConnectionReset

TCP 通、IP 好，只有带 `bitget.com` 的 SNI 被重置。封锁是**概率性**的
（universe 8 小时里漏过 2 次、每次 1 行），所以按"最后一条样本"判断会误判成"没断"。

**② 采样器是直连的，代理对它们从未生效。** 错误日志里
`10054`（远程重置）7,700 条、`10061`（拒绝连接）**0 条** —— 若走代理，
关掉代理必然报 10061。因此"关代理导致断采"不成立：采样器一直是直连。
更关键的是：**`urllib` 的 opener 在进程内首次请求时就定型了**，
所以即便之后系统代理恢复，长驻的采样器也读不到，**必须重启**。

## 5. 处置

1. 确认代理节点恢复：走 `127.0.0.1:7890` 取 `api.bitget.com` 三个端点均 **HTTP 200**。
2. 安全重启（先停监督 → 再停四路 → 清残留锁 → **只起一个**监督）。
   重启前已核实三个采样器的表头写入都是**有条件的**（`new = not exists or size==0`），
   其余一律 `"a"` 追加 —— **重启不会覆盖当天已有数据**。
   锁检查是 `fresh AND pid_alive`，旧锁超 6 小时不 fresh，新实例会正常接管。
3. 恢复验证：四路均写入新行（spread 60 / trades 997 / orderbook 1140 / universe 287，
   样本时刻到 02:24:57），四个 `sampler_*.err.log` **全部 0.0 KB**，无新错误。
