## 🔴 T1：恢复乙侧采样器，并查清是不是同一个封锁

**现状（A 实测）**：乙侧数据停在 **09-15 21:30**，滞后 **45.6 小时**。
甲侧同一时段也断过 8.04 小时，根因是 **ISP 对 `bitget.com` 按 SNI 封锁**。

**请乙执行**：
```powershell
python tools/check_upstream.py          # 判定封锁性质 + 四路采样滞后
python tools/quantify_gap.py            # 算断口大小
```
- `check_upstream.py` 走**裸 socket**，用于判断 ISP 封锁；
- 判断"走代理能否取数"要用 urllib（会读系统代理），二者结论可能不同，别混淆。

**如果确认是同一封锁**：修好代理后**必须重启采样器**才能生效 ——
`urllib` 的 opener 在进程内首次请求时就定型了，之后系统代理恢复也读不到。
安全重启顺序：**停监督 → 停四路 → 清残留锁 → 只起一个监督**。

⚠️ **重启前先确认两件事**（A 已验证过，乙侧请自行复核）：
1. 采样器是**追加写**：表头写入是有条件的（`new = not exists or size==0`），其余 `"a"`；
2. 锁检查是 `fresh AND pid_alive`，旧锁超 6 小时不 fresh，新实例会正常接管。

**为什么这条最紧急**：乙侧的**独立采样**是双机交叉验证的全部依据。
停了 2 天，等于交叉验证这段时间是空的。

3. **是否有 A 漏掉的其他断口** —— 乙侧独立数据是最好的对照；
4. `in_house` 分钟数为 0 这一条**是否成立** —— 它是"影响不大"的唯一支柱，
   如果这条错了，整段结论都要推翻。

⚠️ A 的工具踩过三个坑（已写进注释，乙复核时注意别重蹈）：
- 用"最后一条样本"当断流起点：错。封锁是**概率性**的，偶有单条漏过；
- 用分位数：错。密集数据持续到断点，分位会切掉最后 2% 的正常数据；
- 只找"最后一个大间隙"：错。尾部开口断口后面没有"下一条"，会回溯到几天前的旧断口。
  正解是**从尾部往回连续跨越所有大间隙**。
