## 2. 🔴 定性错误：把「窗口内累计」当成「单笔容量」

**证据**（`data/derived/friction_budget.csv` ← `precise_fill_*.csv`）：

| base | 成交笔数 | `notional_sum_usd` | 每笔中位 |
|---|---|---|---|
| AAPL | 30 | **1,558.06** | 19.01 |
| NVDA | 486 | **125,197.41** | 54.50 |

`capturable_notional_usd` 直接等于 `notional_sum_usd`，而它是
`sum(z * s[j][1] for j, z, _, _ in fills)` —— **整个采样窗口内所有成交的累加**。

它**不是**"单笔能吃下多少"。但交易员把它当作**规模上界**之一：

```
规模上界 = min(请求规模, 可捕获名义额(实测), 首档深度 × 占比上限)
```

后果有两个：

1. **误导读者**：页面上"可捕获名义额 = $125,197"与实时盘口的"≤5bp 可吃 = $231"
   （同一时刻、同一标的）相差 **500 倍**，因为两者根本不是同一种量。
2. **规则失效**：`thin_capacity` 的阈值是 `MIN_NOTIONAL_USD × 10 = $1,000`，
   而所有标的的**累计**值都 ≥ $1,405 —— 这条规则**永远不可能触发**，
   看着像保护、实际是装饰。

**修法（只改口径，不改数值方向）**：标签改成
「样本窗口内**累计**可捕获名义额（非单笔容量）」，并在代码注释里写清它只是**宽松上界**
（实际从不 binding）。**没有**把它删掉 —— 它作为"总盘子有多大"的粗上界仍然有效。

> ⚠️ 没有把 `thin_capacity` 的阈值一起改：那会让一条规则突然开始触发，
> 属于**行为变更**，应由你决定。现状已在注释里标明"该规则在累计口径下不具区分度"。

## 3. 🔴 同类缺陷三处：「缺数据」被当成「无约束」

这一类是本次审计**最危险**的发现。风控系统里，"没有数据"必须按**最坏**处理。

### 3.1 `thin_depth`：缺一条腿反而**不触发**（最危险）

旧写法：

```python
"hit": qty > 0 and min(depth_s, depth_p) > 0 and qty > min(depth_s, depth_p) * RATIO
```

那个 `min(...) > 0` 把"某条腿**根本没有盘口**"判成了**不触发** —— 越危险越放行。

**真实触发场景**：`RSOXLUSDT` 的现货盘口在**交易所侧就是空的**。实测证据：

```
现货盘口 RSOXLUSDT      code=00000 success  bids=0 asks=0     ← 空
现货盘口 RNVDAUSDT（对照） code=00000 success  bids=5 asks=5     ← 正常
现货 ticker RSOXLUSDT    code=00000 success                    ← 但有价格（所以基差还能算）
```

**修法**：`hit` 改为**缺盘口 / 首档为 0 一律触发**；`measured` 同时给出**首档与五档**
（项目自己的 `docs/24` §4.3 已实测"只看最优一档会低估 30–280 倍"，
不能只报首档就下结论）。

### 3.2 规模上界：缺一条腿 → 上界为 0，而不是"跳过这条约束"

旧写法 `if l1 > 0: caps.append(...)` —— 于是"没有深度"**反而变成没有约束**，
一个根本下不了单的腿会悄悄放行整笔单。已改为：

```python
else:
    caps.append(("%s/ask **无盘口**（该腿无法成交）—— 按 0 处理" % venue, 0.0))
```

### 3.3 页面侧同类问题（同一晚修完，见 `docs/46`）

- 容量从"全文件最新一轮"改成**每个标的自己的最近齐全轮**（消除半轮读到的空值闪烁）；
- 缺一条腿的标的**不再显示容量数字**，改标「无现货盘口」且**不参与「基差最大」评选**
  （否则 SOXL 的 −265bp 会永远霸榜，把读者往一个做不了的标的上引）。

## 7. 口径统一（09-19 追加）：页面与决策链共用一份实现

### 7.1 为什么要改

原本**两处各算一份**，而且算法不同：

| | 用的量 |
|---|---|
| 页面 | **5 档 + ≤5bp 滑点**累计（`depth_within_5bp_usd`） |
| 决策链的规模上界 | **首档 × 25%** |

而项目自己的 `docs/24` §4.3 早就写过："只看最优一档会低估 **30–280 倍**，改用 5 档累计"。
**等于文档说 A 对，代码里有一半在用 B** —— 评委把两处并排看就会发现。

### 7.2 三种口径实测（10 个标的，过 100 USD 名义额下限的数量）

| 口径 | 过下限 | 说明 |
|---|---|---|
| A 现状：`min(spot/ask, perp/ask)` 首档 × 25% | 3/10 | 与页面口径不一致 |
| **B 采用：四方向 ≤5bp 累计取最薄 × 25%** | **5/10** | **与页面同口径、带滑点约束** |
| C 裸五档 × 25% | 9/10 | ❌ 不含滑点约束，**属放宽** |

**C 为什么不能用**：GOOGL 现货 bid 的第 2 档就跳到 **11.7bp**，
裸五档算出 30,830，而 ≤5bp 只有 **76** —— 差 400 倍。把它当单笔容量是把
**够不着的档位当成能成交的量**。所以"改用五档累计"必须带上滑点约束。

### 7.3 顺带修掉的一处取侧错误

旧代码写死取 `spot/ask + perp/ask`，但：

* **maker** 模式要 `spot/bid + perp/ask`（买腿挂 bid、卖腿挂 ask）
* **taker** 模式要 `spot/ask + perp/bid`

**两种模式下各错一侧。** 实测盘口强不对称、且方向因标的而异：

| ≤5bp 可吃 | spot/bid | spot/ask | perp/bid | perp/ask |
|---|---|---|---|---|
| **NVDA** | 123,870 | **232** ← 薄 | 507,590 | 7,704 |
| **GOOGL** | **76** ← 薄 | 67,174 | 74,234 | 77,628 |

于是同一时刻有的标的被高估、有的被低估（GOOGL 被高估 884 倍）。
改为**每腿取两侧较薄者、再取两腿较薄者** = 四方向最薄，与页面完全同口径。

### 7.4 收归成一份实现

新增 **`common/book_depth.py`**（放在 `common/` 而不是 `project2/`，
因为项目一有硬约束"删掉 `project2/` 照样完整运行"），
页面 `server/app.py` 与决策链 `project2/agent_team.py` **import 同一个函数**。
收归后逐标的核对：**10/10 完全一致**。

自检（含"打乱档位顺序结论不变"这条，防止依赖文件排列）：

```powershell
python common\book_depth.py      # 8 项
python tools\reproduce_check.py  # 104 项通过 / 0 失败
```

### 7.5 ⚠️ 但要说清楚：这**没有**让策略变得可交易

规模上限从"首档×25%"改成"四方向 ≤5bp 累计×25%"后，上限确实变大了
（如 AAPL 40 → 248、HOOD 63 → 431、TSLA 3 → 2,091），
**但 10 个标的的最终立场仍然全是 `stand_down`** —— 因为真正把它们挡住的是
**另外几条互相独立的约束**：

1. 成本（实测 +10.3 ~ +11.1 bp）贴着门槛 11.34 bp；
2. 现货腿深度仍普遍不足（AAPL/HOOD/MRVL/NVDA/TSLA 的**窗口不足占比 100%**）；
3. 现货腿成交稀疏 → `agent:stale_quotes` 一票否决（META/SPY/TSLA/MRVL）；
4. 逆向选择 `adverse_selection`（GOOGL/HOOD/MRVL）。

**这恰恰是好事**：结论不是被一个参数决定的，而是多条独立证据一致指向"现在不做"。
如果改一个口径就让所有标的变成"可以做"，那才是需要警惕的信号。

> 📌 因此本次改动的价值是：**数字变准、页面与决策链口径一致、不再自相矛盾**，
> 而不是"让项目看起来更赚钱"。


| # | 事项 | 为什么没做 |
|---|---|---|
| 1 | `thin_capacity` 阈值（$1,000）与累计口径不匹配 | 改阈值 = 行为变更，应由你定 |
| 2 | `thin_depth` 是否改用**五档**做单笔上限 | 那会**放宽**规模上限（五档比首档大 25 倍），属于"变宽松"，不能我单方面改 |
| 3 | agent 的容量改用**实时盘口**而非静态 csv | 同上：会显著改变规模结论 |
| 4 | 页面「执行决策」面板与 agent 的容量口径统一 | 需要先定 2/3 |

> 这三条都指向同一个判断：**要不要把"能做多大规模"从"首档 × 25%"改成"五档累计"**。
> 现状偏保守（更小的规模 → 更容易 stand_down），但也因此**更容易错杀**。
> 这是策略口径的选择，不是 bug，需要你拍板。

## 8. 提醒强度：黄 / 红 两档（2026-09-20 · 用户拍板后的实现）

### 8.1 拍板结论

上文 §6 的第 4 条（`thin_depth` 触发判据）**已确认**：

* **保留"首档为基准"**，**不改** ≤5bp —— 该判据只影响"要不要提醒"，不影响规模；
  改成 ≤5bp 会**削弱提醒强度**。用户的判断是"**提醒宁可早**"。
* 因此 §6 那张表里**已无待你拍板的项**（第 1 条 `thin_capacity` 阈值仍未动，属行为变更，
  维持原样）。

### 8.2 新增：统一的提醒强度等级（**只加字段，不改任何判断**）

用户要求：提醒要有**强度等级**，且**两套提醒统一口径**；**不要绿**
（没有提醒就不带等级，不占色位）。所以定义为**两档递增强度**：

| 强度 | 含义 | 决策链风控 `risk_officer` | 持仓期巡检 `position_watch` |
|---|---|---|---|
| 🔴 **红** | 严重：**一票否决** / 裸露敞口 / 事件窗口，必须立刻处理 | `level = veto` | `level = critical` |
| 🟡 **黄** | 值得看：会**改变动作**（缩规模 / 强制吃单 / 收紧），但不否决 | `level = caution` | `level = warn` |
| （无色位） | 没有提醒就不显示 | 未触发的规则 | `level = info`（只记录） |

**实现（单一来源，两处共用）**：

* 新增 `common/alert_level.py` —— 映射 + 取"最严重的一条" + 控制台标签；
  放在 `common/` 而非 `project2/`，因为项目一有硬约束"删掉 `project2/` 照样完整运行"。
* `project2/agent_team.py`：每条规则与风控结论各加一个 `intensity` / `intensity_label` 字段；
  `render_risk` 里**只有触发的那条**才显示强度。
* `tools/position_watch.py`：每条告警加 `intensity` / `intensity_label`；
  `alerts.json` 增加 `intensity_counts` 与整体 `intensity`（前端弹窗可直接取用）。

> ⚠️ **强度不参与决策**：否决/缩规模仍由 `level` / `action` 决定，巡检仍由告警本身决定。
> `intensity` 是**展示层**字段，加它不会让任何标的变得更易/更难通过。
