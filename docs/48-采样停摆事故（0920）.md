### 1.1 关于成交流：四路**确实都停了**；缺口内的 11,517 行是「重启自愈回补」，不是实时采的

本文初稿写「四路全部停摆」。中途我一度据"缺口内 trades 文件有 11,517 行"改判为
「trades 存活但降级」——**那个改判是错的**，已复核推翻。结论回到：**四路采样进程全部停止**。

`data/spread/trades-2026-09-20.csv` 在缺口内确有 **11,517 行**，但**不是实时写的**，
而是 `trades_sampler.py` **重启时自己翻页回补**写进去的（与 `docs/27` 的 0916 那次同源机制）。
判据有三条，第一条即已足以定案：

**判据①（决定性）：每个标的的行数被卡在「约 1 页 = 1,000 笔」**

| base | 缺口内行数 | ≈ 页数 | 若真是实时采样，应有多少 |
|---|---|---|---|
| META | 775 | <1 | 若干千 |
| SOXL | **990** | **1** | **≈ 21,000**（见下） |
| AAPL / SPY / QQQ | 1,012 / 1,007 / 1,033 | 1 | 数千 |
| HOOD / GOOGL / MRVL / TSLA | 1,152 / 1,161 / 1,181 / 1,206 | 1 | 数千 |
| NVDA | **2,000** | **2** | 数千 |

"若是实时采样应有多少"一列取自 `data/backfill/trades-backfill-20260920.csv`
（本人用 `tools/backfill_trades.py --max-pages 40` 拉的交易所全量）：
**SOXL 在那 12.25 小时里有 21,780 笔**，而采样器文件只留了 **990** 笔。
**实时采样不可能把 12 小时的成交压成 1 页**；只有"按页抓取、抓够就停"才会。

代码佐证（`trades_sampler.py`）：

```python
def collect_symbol(symbol, venue, state, limit=1000, max_pages=8):   # L125
    last_ts = state["last_ts"].get(symbol, 0)                        # L130
    first_run = last_ts == 0                                         # L134
    while pages < (max_pages if first_run else 2):                   # L136
        ...
        if not first_run or newly == 0 or oldest is None:            # L169
            break          # 非首次运行 -> 抓完第 1 页就停
```

即：**非首次运行只抓 1 页（1,000 笔）**。state 是持久化的（L109–112 原子写 `STATE`），
所以断流前 `last_ts ≈ 18:48` 仍在 → 重启时算"非首次运行" → 每标的 1 页。
这与观察到的「多数标的 ≈1,000 行、NVDA 2,000 行」**逐项吻合**。

**判据②：首次出现时刻随标的热度阶梯错开**

若行是实时采的，10 个标的应当**从缺口第一分钟就都在**（每轮轮询全部标的）。
实测却是阶梯：

| base | 在缺口内首次出现 | 距缺口起点 |
|---|---|---|
| META / AAPL | 09-19 18:49 | **0 分钟** |
| MRVL / QQQ / HOOD | 18:53 ~ 18:55 | 4 ~ 6 分钟 |
| GOOGL / TSLA | 19:00 ~ 19:01 | 11 ~ 12 分钟 |
| NVDA | 19:48 | 59 分钟 |
| SPY | 09-20 01:48 | 419 分钟 |
| **SOXL** | **09-20 06:14** | **685 分钟** |

规律：**成交越活跃的标的，能"够到"的历史越短**（1 页 = 1,000 笔，
热度越高这 1,000 笔覆盖的时间越短）。这正是分页抓取的签名。

**判据③：最近 1 小时与 40 页全量回补逐位相同**

| 30 分钟桶 | 采样器文件 | 我 40 页回补 |

两者都来自 `fills-history`，在抓全的区段自然逐位相同 —— 反而**不是**实时采样该有的样子
（实时采样有自己的轮询节奏与去重，不会恰好等于全量）。

## 2. 根因（两件事叠加，缺一不可）

### 2.1 直接原因：代理断掉 → 采样器 SSL EOF 退出

`data/logs/sampler_core.err.log` 的最后写入时间是 **09-20 02:47:33（本地）= 09-19 18:47 UTC**
—— 与数据停写的时刻**完全吻合**。尾部内容是同一形态的错误刷屏：

```
[warn] spot RMRVLUSDT: URLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING] ...'))
[warn] perp MRVLUSDT:  URLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING] ...'))
[warn] spot RTSLAUSDT:  URLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING] ...'))
[warn] perp TSLAUSDT:   URLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING] ...'))
```

这和 **09-18 那次**（`docs/27`）是同一个签名：**代理节点挂了**。直连被 ISP SNI 阻断
（`WinError 10054`），所以代理是唯一通路。

### 2.2 🔴 真正的系统性原因：**没有任何东西会把它们拉起来**

| 环节 | 状态 |
|---|---|
| 守护进程（`sampler_supervisor.ps1`） | **早就死了** —— `data/logs/supervisor.log` 最后一条是 **09-17 02:21:57** |
| 开机自启计划任务 `BitgetS2_SamplerGuard` | **不存在**（`Get-ScheduledTask` 里查不到） |

所以：守护 09-17 就没了 → 没人监控采样器 → 代理在 09-19 18:47 一断，四路一起退出
→ **躺了 12 小时没人知道**。

> 这才是要修的东西。代理会再断（它已经断过两次），但**断 5 分钟和断 12 小时的区别，
> 就在于有没有守护和自启**。

### 3.2 让它不再发生（已完成，且**验证过不会拉出第二套**）

`install_sampler_guard.ps1` 注册计划任务需要管理员权限 → **被拒**，它自动回退到
启动文件夹（`Startup\BitgetS2_SamplerGuard.cmd`，登录时启动）。
但那**只覆盖登录时刻** —— 长时间登录期间守护若挂掉仍无人拉起。所以另外用

```powershell
schtasks /Create /TN "BitgetS2_SamplerGuard_Min" /SC MINUTE /MO 10 /F `
  /TR 'powershell.exe -ExecutionPolicy Bypass -NoProfile -WindowStyle Hidden -File "...\scripts\sampler_supervisor.ps1"'
```

**每 10 分钟**跑一次守护。安全性来自守护自身的单实例锁：
**已有守护存活 → 新实例立刻退出**，不会出现"两个守护各拉一套采样器"
（那正是 `sampler_supervisor.ps1` 头部警告过的、会导致同一 CSV 被交错写入的坑）。

**实测验证**（手动触发一次任务）：

```
触发前：spread=21024 ｜ universe=21412 ｜ orderbook=8424 ｜ trades=25548
触发后：spread=21024 ｜ universe=21412 ｜ orderbook=8424 ｜ trades=25548   ← PID 未变
守护日志：没有新增"守护进程启动"条目                                 ← 第二次守护自己退出了
```

✅ 幂等、不重复。三层防线的最终形态：

```
登录 → 启动文件夹拉起守护
每 10 分钟 → 计划任务再拉一次（已有守护则空跑）
守护存活期间 → 采样器退出后 10 秒自动重启
```

## 6. 缺口能补回多少？（2026-09-20 追加）

先回答一个自然的想法：**"能不能用乙侧样本补？"—— 不能。** 实测核对：

| 项 | 值 |
|---|---|
| 乙侧提供的**不可回补类**数据 | 只有 `data/b-side/spread/*.csv`（**最优一档**报价） |
| 乙侧盘口总跨度 | `2026-09-12 15:14` → `2026-09-14 16:51` |
| 距我的缺口起点（09-19 18:47） | **还差 121.9 小时（5 天）** |
| 乙侧有没有 orderbook / 逐笔成交 | **没有**（`orderbook*` 无文件；`backtest/trades.csv` 是回测结果不是市场成交） |

所以乙侧数据**时间上差 5 天、类型上也缺**，补不了。

### 6.1 ✅ 但逐笔成交可以从交易所补回来

`fills-history` 端点保留最近若干笔（实测**永续 8000 笔 / 现货 2000+ 笔**），
而周末行情清淡 —— **这 8000 笔往回翻能覆盖到缺口起点之前**。
实测 NVDA 永续：8 页 8000 笔 → 最早 `09-19 18:03`，早于缺口起点 `18:47`。

新增工具 `tools/backfill_trades.py`：

```powershell
python tools\backfill_trades.py --gap-start 2026-09-19T18:47:23Z `
                                --gap-end   2026-09-20T07:03:26Z
```

**结果：20 个（标的 × 腿）里 20 个全部翻到缺口起点之前**，回补 **43,625 笔**
（缺口内平均 59.3 笔/分钟），落在
`data/backfill/trades-backfill-20260920.csv`（5.79 MB，100% 行落在缺口区间内）。

### 6.2 🔴 三条红线（否则这个工具会变成"伪造连续性"的帮凶）

1. **绝不写进 `data/spread/trades-*.csv`** —— 那是采样器的文件。混进去会让
   `find_gaps` / 覆盖率日报**看不见缺口**。已实测确认：回补后
   `find_gaps` **仍然报 736.1 分钟缺口**（这正是要的结果）。
2. **每行标 `source=exchange_backfill`**，谁都能分清哪些是当时采的、哪些是事后补的。
3. **补不到就空着** —— 超出保留窗口的不猜、不插值。（本轮 40 页上限内全部够到；
   若某标的成交更密，翻页到保留上限仍未覆盖，就如实标"❌ 否"。）

### 6.3 仍然补不回来的：**盘口（5 档深度）**

交易所**没有**盘口历史接口（这是本项目从第一天就写进 `docs/DATA_DICT.md` 的事实）。
所以缺口对这 12h16m 的**深度/点差形状**是永久损失，只能如实标注。

**影响的边界（说清楚，不夸大也不缩小）**：

| 分析 | 是否受缺口影响 |
|---|---|
| 联合成交分布（`docs/14` §9，09-12~09-14） | **不受影响**（窗口在缺口之前） |
| route 对照 / 越线率（`docs/15`） | 轻微：样本减少，但结论来自 8 天窗口 |
| 成本模型标定（盘口实测） | 轻微 |
| 当前 `in_house` 窗口的**深度形状** | **受影响**（这段盘口没了） |
| 当前窗口的**成交轴** | ✅ 已由回补恢复 43,625 笔 |

### 6.4 顺带一提：乙侧数据仍然有用

它覆盖的 `09-12 ~ 09-14` 正好是**联合成交分布**那个窗口，
而它又是**另一台机器独立采集**的 —— 对"跨机器一致性"（`docs/30` §3，572 组重叠
样本中间价相对差中位 0.00 bp）是**唯一的第三方证据**。所以它补不了缺口，
但支持了另一件更重要的事：**数据本身可信**。
