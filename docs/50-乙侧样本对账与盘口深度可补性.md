## 4. 结论：乙侧样本能补什么、不能补什么

> ⚠️ **本节结论已于 2026-09-20 深夜修订**（原写"能补的只有 114 轮"）。
> 修订原因见 §3 的红色注记与 §6。

**不能补的**：

1. **5 档深度一处都补不了** —— 覆盖率 **0%**。乙侧根本没有 `level` / `cum_notional_usd`
   这些字段（只有 `bid/ask/mid/bid_sz/ask_sz`）。**这是类型上的不可能，与时间无关。**
2. **补不了窗口起点** —— 平台 `in_house` 窗口自**周六 08:00（北京）**起，
   而三方最早一轮分别是：我方 5 档 `09-13 01:25`、我方首档 `09-12 21:01`、
   乙侧 `09-12 23:14`。**都晚于 08:00**，那一段任何一方都没有数据，
   **永久不可回补**（乙侧自己的 `说明.md` 也承认它那侧空了 15.2 小时）。
3. **其余 5 处小缺口（合计约 907 分钟）补不了** —— 乙侧那几段没采。

**能补的**：

| 项 | 数量 |
|---|---|
| 乙侧有、我方 **5 档**没有 | **847 轮** |
| 其中连我方**首档**也没有（**真正新增的信息**） | **755 轮**（= 14,694 行） |
| **最大的一块** | **09-20 02:48 → 15:09（北京）734 轮** = 我方 12h16m 停摆缺口，**覆盖 100%** |
| 另一小块 | 09-12 23:14 → 09-13 01:24（北京）114 轮 = 窗口头部 |

> **勘误（2026-09-20 复核）**：本行原写「09-13 01:12 → 01:24（北京）= 09-12 17:12 → 17:24 UTC」，
> 与同一行的「114 轮」**自相矛盾** —— 12 分钟装不下 114 轮。
> 直接对 `data/derived/bside_supplement_topofbook.csv` 数 distinct `ts_ms`：
> **114 轮**，跨度 **130.6 分钟**（0.87 轮/分），起止正是 **09-12 15:14:12 → 17:24:47 UTC**。
> 行数（114 轮 / 2,271 行）本身是对的，**只有时段文字写错**，已按实测更正。

也就是说：我方 5 档起点是 09-13 01:25（北京），而乙侧**正好采到了它前面的约 130 分钟
（09-12 23:14 → 09-13 01:24）的首档深度** —— 对"最早的深度窗口"这一点，
它是**唯一的第二个来源**。

> 注意口径：这 114 轮给的是**首档深度**，**不是 5 档**。
> 它可以回答"那一刻盘口有多厚（第一档）"，不能回答"≤5bp 能吃掉多少"。
> 两者不可互相替代（本项目 `docs/14` §3.2 记过"顶部挂单深度"与"已成交名义额"给出相反瓶颈腿结论）。

## 8. 本轮踩到的两个坑（留档）

### 8.1 只算"文件内部"缺口 → 漏掉 0916 那 8 小时

第一版把每个 `orderbook-*.csv` 单独算相邻两轮的间隔，于是
**09-16 18:19 → 09-17 02:20 这 481 分钟整个消失了** ——
因为它正好**跨两天**（前一个文件的结尾 → 后一个文件的开头）。
修正：必须按**全局**时间轴算缺口。修正后缺口从"1161 分钟"变成**1642 分钟**。

### 8.2 新工具缺控制台编码兜底 → 自检直接变红

`reproduce_check` 里有一条"所有工具的控制台编码兜底齐全"的检查
（事故驱动：`kline_accumulator.py` 曾因 print ⚠️ 在 GBK 控制台崩掉，
而它注册在开机启动里 → 每日自动补齐静默失败）。

我新写的 `audit_manifest_b.py` 里有一行 `print("      ✗ %s" % x)`，
**`✗`(U+2717) 不在 GBK 里** → 直接被判红：

```
[!!] 有 1 处会被 print 的非 GBK 字符，且没有任何兜底
     -> Windows 控制台下会抛 UnicodeEncodeError 并中断整个脚本
```

修法：三个新工具都装上项目统一兜底 ——

```python
sys.path.insert(0, BASE)
try:
    from common.console import install as _install_console
    _install_console()
except Exception:
    pass
```

复查：`python tools\check_console_encoding.py <files...>` → **缺兜底且有 print 风险的文件：0**。

> **教训**：本项目规定"任何会在 `.cmd`（GBK 控制台）里被调用的工具都必须装编码兜底"，
> 新写工具时**一开始就要带上**，别等自检变红。

### 8.3 顺带说明：`tools/audit_bside_coverage.py`

它是本轮先写的"逐轮对账"脚本，功能已被 `gap_capacity_report.py` 覆盖（后者是超集）。
本想删掉，但**本机沙箱的 safe-delete 把它拦下了**（`rm` 报成功、文件其实还在）。
处置：**保留**，在文件头注明"已被 `gap_capacity_report.py` 取代"，
并补上编码兜底。要清理的话手工删即可 —— 它未进版本管理。

## 9. 全量自检偶发变红 → 挖出两个**真缺陷**（已修 + 已证明）

本轮跑 `reproduce_check` 时，出现了一次 `前端布局验收失败`，**而产物里没有任何 `[!! ]` 行**，
只有一句"见 tools/ui_check.py 输出"。这种事不能以"偶发"收场，于是逐层挖下去。

### 9.1 缺陷一：前端取数"一个接口失败拖死整组"

`web/app.js` 的 `refresh()` 原本是：

```js
const [ov, ses, st] = await Promise.all([
  api('/api/overview'), api('/api/session-compare'), api('/api/data-status'),
]);
```

**任意一个接口瞬时失败 → 整组 reject → `DATA` 三个字段全为 null →
`renderAll()` 什么都不画 → 骨架屏永远留在页面上。**
而真浏览器验收的等待条件正是"页面里没有 `.sk`" → 浏览器等到超时 →
报"浏览器没跑出结果"。**接口是偶发的，表现却是"页面卡死"** —— 最难查的那一类。

**修法**：
1. `fetchOne()` 逐个取，谁到了渲染谁（单接口失败不再影响另外两个）；
2. 有缺失时点亮错误灯，并**最多补 3 次**（3 秒一次），不全成功就停手；
3. 新增 `sweepSkeletons()`：**25 秒后把残留骨架屏换成一句"暂时取不到数据"** ——
   从根上消灭"永久转圈"，也顺带满足探针的 `stuck_loading` 语义。

**证明（故障注入，不是嘴上说）**：起一个临时实例把 `/api/session-compare` 改成恒定抛错，
再用**与自检完全相同的等待条件**跑探针：

| 探针项 | 修复后实测 |
|---|---|
| `sk_count` | **0**（修复前会永远 >0） |
| `fallback_count` | 1（文案"暂时取不到数据 —— 请确认本地服务在运行"） |
| **`rows_pairs`** | **10** ← 关键：一个接口挂了，配对表照常渲染 |
| `rows_session` | 1（该表显示兜底文案） |
| `rows_assess` / `rows_opp` | 20 / 2（其它面板不受影响） |
| `live_dot` | `dot err`（如实点亮错误灯，不假装健康） |

### 9.2 缺陷二：验收脚本自己把失败原因吞了

`reproduce_check` 里提取失败原因的代码是：

```python
_why = " ｜ ".join(x.strip() for x in _lines if "[!! ]" in x)[:170]
```

但 `ui_check` **首次截图失败**走的是另一条分支，打的是 **`[FAIL]`**（不是 `[!! ]`）：

```python
if not os.path.exists(out_json):
    print("  [FAIL] 浏览器没跑出结果（退出码 %d）" % p.returncode)
```

于是**真正的原因被过滤掉了**，汇总里只剩"见 tools/ui_check.py 输出"。
**验收脚本把原因吞掉，本身就是缺陷** —— 下次再红，人还是查不到。

**修法**：
1. `reproduce_check` 的原因提取同时匹配 `[!! ]` 与 `[FAIL]`；
2. `ui_check` 的首次截图**失败重试一次**（headless Chrome 高负载下冷启动失败是真实存在的），
   重试仍失败时明确打印
   "**这**不是**布局问题，是本机浏览器/负载问题**" —— 把"偶发"和"真回归"分开。

## 10. 结论（一句话）

**分两句说，因为答案在 09-20 深夜变了：**

**（1）5 档深度：一段都补不了。** 乙侧根本没有 5 档字段（只有 `bid/ask/mid/bid_sz/ask_sz`）——
这是**类型上的不可能**，与时间无关。那 1,642 分钟的**深度形状永久丢失**。

**（2）首档点差：最大的一段补上了。** 乙侧 W2 样本（`git fetch` 后新增的
`2026-09-18/19/20.csv`）**恰好覆盖我方 12h16m 停摆缺口**：
**732 轮 / 14,634 行 / 分钟覆盖 99.7%**，且全落在"我方连首档也没有"的分钟上。
导出到 `data/derived/bside_supplement_topofbook.csv`（**16,925 行**，
其中 **14,694 行**是我方完全没有的），按"保留来源标记 / 按轮去重 / 不插值"三条纪律，
实测三条全守（`source` 全为 `b-side`、重复键 0、每行都能在乙侧原始文件里找到）。

> ⚠️ 引用这份补录时**必须带上口径边界**：它只能回答"那一刻最优一档的点差与挂单量"，
> **不能**回答"≤5bp 能吃掉多少"（那要 5 档累计，乙侧没有），
> 也**不能**用它的轮次密度做时间加权（它是另一台机器）。
> 详见 `docs/51` §6.4。

它另外的价值是**双机对照复核**（中位差 0.00 bp，证明我方数据可信）。
