# 52 · 小白三问视图（「怎么做」）

> **起因**：用户提问 —— *「如果我是一个散户小白，我要在这个程序上简洁明了清晰地明白
> 我什么时候要买入、什么时候卖出、什么时候有风险？」*
> 本文记录这一版**新默认视图**的设计、判据出处，以及实现过程中踩到的四个坑。

---

## 1. 为什么原来的页面答不了这个问题

改版前的三个视图是按**证据类型**组织的，不是按**用户要做的决定**组织的：

| 视图 | 回答的问题 | 对新手的问题 |
|---|---|---|
| ② 现在看盘 | 10 个标的的基差/点差/深度各是多少 | 看完不知道该干嘛 |
| ③ 该不该做 | 每个标的的风险等级与理由 | 10 行"谨慎"，没有"那我该做什么" |
| ④ 凭什么信 | 分时段点差 / 数据状态 | 这是给评委看的证据，不是给用户看的结论 |

更关键的是：**页面上根本没有"什么时候卖"**。平仓规则（门槛 0 bp、最长持有 48 小时）
在 `common/strategy_params.py` 里写着，但从来没往页面上传过。
于是"买"能看个大概，"卖"完全看不到 —— 而这门生意恰恰是**两条腿进出、必须知道什么时候出来**。

---

## 2. 三问的答案（全部来自已有规则，本轮**不新增任何阈值**）

### ① 现在能买吗

四道判据，**全部打勾**才叫能做。顺序即代码里的 `if/elif` 顺序（先卡哪一条排前面）：

| # | 判据 | 出处 |
|---|---|---|
| 1 | 处于**所内撮合窗口**（`route == in_house`） | `common/market_calendar.route_of` |
| 2 | **有标的**的两条腿盘口齐全 | `build_overview` 的 `tradable` |
| 3 | 基差 ≥ **11.34 bp** | `common/strategy_params.ENTRY_THR_BP`（= 回测 `main_cfg.entry`） |
| 4 | **扣掉执行成本后还有空间**（净 > 0） | `basis_bp − best_cost`，两侧都是既有字段 |

> 第 4 条是这一版**最重要的一条**，也是最容易被漏掉的一条：
> 门槛 11.34 bp 只是"费用线"，真正决定赚不赚的是「基差 − 实际执行成本」。
> 实测中 HOOD 基差 50+ bp、净 +39 bp，而 META 基差 13.7 bp、净只有 +3.5 bp ——
> 只看门槛会把这两者当成一回事。

**做法**（写在页面上，避免"买入"被误读成买股票）：

> 开仓 = 同时下两条腿：**买现货 + 卖永续**。方向相反，涨跌互相抵消，
> 只赌两者的价差收窄。**必须一起成交** —— 只成交一条腿就变成裸的方向敞口。

### ② 什么时候卖

三条规则，**满足任意一条就平**。全部取自 `common/strategy_params.py`：

| # | 条件 | 为什么 |
|---|---|---|
| 1 | 基差回落到 **≤ 0.00 bp** | 赚的就是「开仓基差 − 平仓基差」；回到 0 表示空间收完 |
| 2 | 持有满 **48 小时** | 回测里到点强制平仓，避免"再等等看"把收敛拖成套牢 |
| 3 | 出现**风控告警**（黄/红） | 按告警给的处置做（补腿/撤单/缩规模），不自行判断 |

### ③ 现在有没有风险

两个来源，分开呈现、**互不冒充**：

- **持仓类风险** —— 来自 `tools/position_watch.py` 落盘的巡检告警（只有黄/红两档，**没有绿**）
- **结构性风险** —— 来自机会名单的聚合：「今天挡在门外的是：有一条腿没有盘口 ×1、基差没到门槛 ×8」
- **引擎横向判定** —— 风险引擎的 high/medium/low 分布（实测 1 / 9 / 0）

## 3. 接口：`/api/signals`

新增 `build_signals()`（`server/app.py`）。设计红线：

1. **不产生任何新判断、不定义任何新阈值** —— 只把 `build_opportunities()`、
   `common/strategy_params`、`build_alerts()`、`build_assess()` 四份既有结果翻译成白话；
2. **这条链路上没有 LLM** —— 模板是确定性的，所以不存在"编一个理由"的可能；
3. 失败返回 `available: false` 并说明原因，**绝不退化成"看起来一切正常"**。

状态词表（每一格都由后端给，前端只渲染）：

| 卡 | `state` | 含义 |
|---|---|---|
| 买 | `ready` | 四道判据全过 **且引擎说「可执行」** |
| | `caution` | 判据全过，但引擎给的是「谨慎（缩小规模 / 放宽价位）」 |
| | `wait` | 窗口内，但基差没到门槛 / 净空间为负 |
| | `off_window` | 不在所内撮合窗口（附**下一个窗口的北京时间与倒计时**） |
| | `no_data` | 取不到盘口 —— **既不说能买、也不说不能买** |
| 卖 | `holding` / `flat` / `stale` / `unknown` | 持仓状态；`stale` = 巡检快照已过期 |
| 风险 | `red` / `yellow` / `none` / `stale` / `unknown` | 持仓类风险；结构性风险另行照常给 |

## 4. 实现过程中踩到的四个坑（留档）

### 4.1 `ready` 差点乱给 —— 门槛是这套系统里最浅的一层

第一版把"过了门槛"直接映射成 `state = "ready"`，页面就会显示**可以开仓**。
但实测：过门槛的 HOOD / META，风险引擎的结论都是「谨慎」 ——
引擎还有它自己的顾虑（成本为正、腿风险）。

**修法**：`ready` **只留给引擎自己说「可执行」**的时候；判据全过但引擎说谨慎 →
单独一个 `caution` 态。这样页面永远不会给出比引擎更乐观的结论。

### 4.2 顺带查清：引擎为什么**永远**最多只给「谨慎」

`project2/event_gate.py` 的分级逻辑是：

```python
over = bool(cost and cost.get("best_cost", 0) > 0)     # 执行成本为正
thin = bool(cost and (cost.get("p_part") or 0) > 0.5)  # 只成交一腿概率 > 50%
if over and thin:  high, "不做（成本为正且腿风险高）"
elif over or thin or sev == "caution":  medium, "谨慎（缩小规模 / 放宽价位）"
else:  low, "可执行（仍有风险，非稳赚）"
```

**执行成本恒为正**（挂单也要付手续费），所以 `over` 恒为真 ⇒ `verdict == "可执行"` 实际不可达。
根因是 `assess()` 的签名里**没有基差**，它无法判断"基差够不够覆盖成本"，
只能用 `cost > 0` 这个更粗的判据（它的警告文案本身就写着"若基差不足以覆盖，这一单不应做"）。

这是**引擎的保守设计**，不是 bug；但小白页不能替它转述成"不能做"。
所以页面把这件事**明说**出来（`buy.engine_note`）：

> 风险引擎这一层的口径是只看成本是否为正，它拿不到基差，所以无法判断
> 「基差够不够覆盖成本」—— 因此只要成本为正，它最多只会给「谨慎」。
> 真正判断赚不赚要看上面第 ④ 条的净空间。

### 4.3 两天的旧告警被当成"现在的事"

`alerts.json` 是**落盘快照**。头寸平掉、持仓单 `data/positions/open.json` 删掉之后，
这份文件**不会自己消失** —— 结果 09-20 打开的页面上，弹出的是 **09-18 的红色告警**，
而持仓单早已不在。（`position_watch.py` 在没有持仓单时会提前返回、**不写文件**，
所以磁盘上那份永远是最后一次有持仓时的样子。）

**修法**：`/api/alerts` 增加两个字段 ——

- `tracked`：`open.json` 在不在（决定这批告警算不算"当前"）
- `stale`：快照是否超过 `ALERT_STALE_MIN = 180` 分钟

没有 `tracked` 时：风险卡的红/黄**归零**，告警收进 `historical_alerts` 计数，
文案改成"另有 N 条已结束头寸的历史告警（不计入当前）"；右下角弹窗也不再弹。

### 4.4 一条腿缺盘口，不该让整条判据打叉

判据 ② 第一版按"是不是**个个**都齐全"判。SOXL 缺现货盘口 ⇒ 打叉，
于是同一张卡上同时出现「× 两条腿的盘口都在」和「✓ 基差够门槛（有 1 个标的达标）」——
新手会读成"不能做"，与结论矛盾。

**修法**：判据 ② 问的是"**有没有能成交的标的**"（`tradable ≥ 1`）。
缺腿的标的在机会名单里已被排除，**它不挡别人**，所以降级为括号里的提示。

## 5. 前端

- 新增默认视图 `signals`（页签「① 怎么做」），原来的三个视图顺延为 ②③④；
- 一句话结论条（含确定性优先级：红告警 > 可开仓 > 谨慎 > 非窗口 > 无数据 > 差多少）；
- 三张卡 + 「这三张卡怎么读（30 秒版）」折叠；
- **配色纪律**：绿只给"引擎明确说可执行"（当前口径下几乎不出现）；
  风险轴的「当下没发现要处理的」用**中性色**，不给绿 ——
  与既有的「提醒只有黄/红两档，没有绿」保持一致。

| 位置 | 检查 |

| `reproduce_check` 静态 | `def build_signals(` / `def next_in_house_start(` / `blocked_code` / `renderSignals(` / `view-signals` / `sig_badges_blank` |
| `reproduce_check` 契约 | **`/api/signals` 不变量**：4 条判据齐全、`risk.tracked` 存在、3 条平仓规则、<br>**`state ∈ {ready, caution}` ⇒ 四道判据必须全过**（防止给出比判据更乐观的结论） |
| `ui_probe.js` | `sig_cards` / `sig_checks` / `sig_badges_blank` / `sig_states` / `sig_headline_blank` |

> ⚠️ 同时修了一个**覆盖率回归**：`ui_check.py` 的视图轮询原本是
> `("decision", "evidence", "all")`。默认视图改成 `signals` 之后，
> `monitor` 既不是默认、也不在轮询里 ⇒ **它会变成完全没人测的视图**。已补进轮询串。

## 8. 后续：测算金额输入（2026-09-21 追加）

用户提问：「添加一个输入我需要计算的金额，而不是默认多少金额去计算」。

### 8.1 做了什么

- 页面顶部新增「按 $ ___ 测算」输入框，**持久化到 localStorage**、防抖 500ms；
- 后端 `/api/signals`、`/api/opportunities`、`/api/assess` 三个端点接受 `?size_usd=`；
  **三个端点必须一起重取** —— 只改一个会让「怎么做」与「机会名单」显示两套金额下的数；
- 回落规则明确（`parse_size_usd`）：空/非法 → 默认并**说明原因**；<$10 或 >$1M → 默认并说明。
  **刻意不静默夹取** —— 否则用户会以为屏幕上是他填的金额，而其实是另一个数；
- 页面新增一行「这个金额影响什么、不影响什么」，防止"填大一点就能过门槛"的误解。

### 8.2 顺手挖出并修掉的三个真问题

| # | 问题 | 为什么危险 | 修法 |
|---|---|---|---|
| 1 | **三处缓存都是单条目** | 加了金额参数后，改成 $50,000 会拿到**上一次 $5,000 的结果** —— "能吃掉多少""净剩多少"全是错的，而页面数字看着很正常 | 三处缓存全部**按 size_usd 分键**；并加进 `reproduce_check` 的接口契约（不同金额必须各自生效） |
| 2 | **实时行情部分刷新会整块覆盖缓存** | `fetch_live()` 对失败的符号是 `except: pass` 静默跳过。连抓 8 次实测 OK 数 = `[20, 20, 20, 18, 20, **7**, **11**, 10]` —— 一次抖动让 **13 个符号**瞬间变成"没有实时行情"，页面从"4 个候选"抽搐成"取不到盘口"，几十秒后又变回来 | 新增 `_merge_live()`：**新值优先，新值缺的符号保留旧值**；但旧的超过 `LIVE_MAX_AGE_SEC = 180s` 就丢弃（不把几分钟前的价当现价）。同时把 `quote_age_sec` 露到接口上 |
| 3 | 改金额后页面**僵住数秒且无提示** | 每个新金额都要重算双腿模型（冷态实测 ~5s），用户会以为输入框坏了 | 加「正在按 $X 重新测算…」状态 + 15 秒兜底清除 |

**修后实测**：连打 12 次 `/api/signals`，候选数**稳定为 2**（修前会在 0 和 4 之间跳），
`quote_age_sec` 如实显示 9.8s → 42.0s（某个符号扛过了一次部分刷新）。

### 8.3 一个**没有修**的建模边界（如实记下）

`project2/execution_cost.py` 的 `analyse_two_leg(base, qty_usd, …)` **收了 `qty_usd` 却一次都没用**：
三个成本式（`cost_mm` / `cost_mix` / `cost_tk`）全由费率、半幅点差、逆向漂移与成交概率构成，
**没有规模冲击项**。而同一个文件里**单腿**路径的吃单成本是**含**冲击的
（`cost_taker = half + fee_taker + imp`）—— 同一概念两套实现。

- 对**挂单做市**（策略实际选的情形）而言，每单位成本与规模无关是**可辩护的**：挂单没有吃穿盘口的滑点；
- 但 `cost_tk`（双腿全吃单）是**吃单**场景，那一行**确实偏乐观**。

**因此本轮没有改模型**（会动到已发布数字与项目二的独立提交），而是在接口里新增
`size_scope` / `size_scope_full` 把这条边界**写在页面上**，并在这里留档。
是否补上冲击项，留给用户决定。
