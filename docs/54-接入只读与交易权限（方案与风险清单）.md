# 54 · 接入只读 / 交易权限：方案对比与风险清单

> 起因：用户问 —— *「如果我给交易权限，风险是不是就提高了？是否会导致胡乱下单？」*
> 以及 *「新面板是什么面板？是新端口，还是项目端口下的新功能切换页？」*
>
> **本文只做决策材料，不含任何下单代码。** 目前仓库里**没有任何签名请求、没有任何下单能力**
> （实测：`ACCESS-SIGN` / `ACCESS-KEY` / `hmac` 对 Bitget 的引用为 **0**，
> 所有 Bitget 调用都是公开端点）。

---

## 0. 先回答"风险是不是提高了"

**不是"给了交易权限就会胡乱下单"。** 胡乱下单来自另外两件事，而这两件都可以设计掉：

| 真正决定风险的是 | 不是 |
|---|---|
| ① **有没有自动化触发**（没人点也下单） | 有没有给权限 |
| ② **下单前有没有强制前置校验** | 页面上有没有按钮 |

**你说"不给自动化交易权限"——那就已经砍掉了最大的那一块。**
只剩"你在场、你点、它才发"这一种形态，系统**没有能力**自己下单。

> 一句话：**密钥给了 ≠ 系统会下单。** 下单能力应该由一个**默认关闭的显式开关**控制，
> 开关不打开时，即使 `.env` 里放着有交易权限的 key，代码路径也根本走不到下单。

## 1. 三个方案（请挑一个）

| | 方案 A：只读 | 方案 B：只读 + **手动**补腿 | 方案 C：自动补腿 |
|---|---|---|---|
| 需要什么 key | 只读 | 只读 + 交易 | 只读 + 交易 |
| 系统能下单吗 | ❌ 完全不能 | ✅ **只有你点那一下** | ✅ 成交即触发 |
| 能看见真实仓位/资金吗 | ✅ | ✅ | ✅ |
| 能做的是 | 显示 | 显示 + 执行**引擎已给出的**动作 | 全自动 |
| 新风险 | 密钥泄漏（只读，最坏是被人看到余额） | 误点 / 重试 / 状态过期 | 无人值守下的连锁下单 |
| 我的建议 | 至少做这个 | **如果你愿意在场，这个最实用** | ❌ 不建议（你自己的判断也是对的） |

**方案 B 的关键性质**：它**不产生任何新判断**。
按钮能执行的动作，只能是确定性引擎**已经算出来**的那一个
（项目已有的动作词汇：`no_new_position` / `cap_size` / `require_taker`，
外加告警里的 "补上缺失的那条腿" / "平掉已成交的那条腿"）。
**LLM 永远不产生动作** —— 它只做新闻分类。所以"胡乱下单"在结构上没有入口。

## 2. 就算只做方案 B，也必须有的 7 道护栏

这些不是理论风险，每一条都对应一个具体的下单事故：

| # | 事故 | 会发生什么 | 护栏 |
|---|---|---|---|
| 1 | **重复补腿** | 双击 / 超时重试 → 下出**第二条**补腿单 → 从"缺一条腿"变成"反方向多一条腿" | 幂等键 + 下单前重读真实持仓 + 按钮立刻禁用 |
| 2 | **补错方向** | 以为缺永续腿，其实缺的是现货腿 | **每次下单前重新读交易所真实持仓**，绝不信任页面上的旧状态 |
| 3 | **补错数量** | 用页面上的"建议规模"，而实际成交的那条腿是另一个数 | 数量**由真实成交腿反推**，不用页面数字 |
| 4 | **不该补的时候补** | 其实两条腿都成了（限价单延迟回报） | 下单前必须确证"一条成了、另一条没有"，否则拒绝 |
| 5 | **超出余额/保证金** | 下单被拒，或部分成交留下新的裸露 | 下单前查可用余额，超过就**拒绝**而不是硬发 |
| 6 | **价格失控** | 市价补腿在薄盘口上吃穿 5 档，把 3 bp 的问题变成 30 bp | **只发限价单 + 滑点上限**，超限就拒绝（宁可裸露也不硬吃） |
| 7 | **密钥泄漏** | 交易权限的 key 落到别人手里 | 只放 `.env`（`.gitignore` 已覆盖），**永不进代码/文档/日志**；不用就删 |

**另外两条工程要求：**

- **默认 dry-run**：第一次点"补腿"只**打印**它将要发的请求（标的/方向/数量/价格/预估费），
  要再点一次确认才真发。这样"手滑"最多是看到一段文字。
- **开关与密钥分离**：`TRADE_ENABLED=off` 是默认值；即使 key 有交易权限，
  开关没开时下单函数直接返回"未启用"。**让"不能下单"成为默认状态，而不是默认能力。**

## 3. "新面板"是什么？—— 是我上一轮没说清

三个可能，我先说结论：**推荐第二个（同一个端口下的新页签）**。

| 形态 | 长什么样 | 代价 |
|---|---|---|
| ① 新端口（如 8788 再起一个服务） | 两个地址、两个页面 | ❌ 多一个常驻进程要守（本项目已经因为"没人守"出过 12 小时断流）；两份数据要同步；自检要覆盖两棵树 |
| ② **同一个 8787 端口下加一个页签「⑤ 我的账户」** | 和现有 ①怎么做 ②现在看盘 ③该不该做 ④凭什么信 并列 | ✅ **零新进程**，共用同一条数据管线、同一套自检、同一个 URL |
| ③ 塞进现有卡内（如「什么时候卖」卡下面加一块"我的持仓"） | 不新增页签 | ⚠️ 首页会变长；而且账户信息属于"按需查看"，不该占首屏 |

**所以：不新开端口，也不是替换现有页面 —— 就是现在这个 `http://127.0.0.1:8787` 下面多一个页签。**

那个页签会长这样（**只读部分先做，与交易权限无关**）：

| 区块 | 内容 |
|---|---|
| 账户总览 | 可用余额 / 持仓市值 / 保证金占用（来自只读 API） |
| 我的持仓 | 每个标的的两条腿：成交量、成交价、开仓时间、当前基差、浮动盈亏 |
| **资金变化** | 从开仓到现在的**实际余额变动** —— 这才是真实的 P&L（现在页面上那个"净 +52.71 bp"只是**预测**） |
| 该不该平 | 直接标出哪些持仓**已经满足平仓条件**（基差 ≤ 0 / 满 48 小时） |
| 待处理 | 只成交一条腿的持仓（红色）—— 方案 B 下这里会出现「补腿」按钮 |

## 5. 用户的决定与本轮实现（2026-09-21）

**用户答复**：① **方案 B**（只读 + 手动补腿）；② **同一账户**（现货与永续在同一个 Bitget 账户）；
③ key 勾**只读 + 交易**。

用户还提了一个关键要求，它直接决定了实现方式：

> 「不能够通过我同一账户下的仓位进行审查我是否有两腿下单吗」

**能，而且这就是本轮采用的做法。** 既然两条腿在同一个账户，只读 API 就能同时看到
现货资产（`RHOODUSDT` 余额）与合约持仓（`HOODUSDT` 仓位），
于是**"我到底有没有两条腿"由交易所的真实状态判定**，
不再依赖手写的 `data/positions/open.json`，也不信任页面上的旧状态。

### 5.1 本轮已实现（**都可以在没有 key 的情况下验证**）

| 文件 | 内容 |
|---|---|
| `common/bitget_private.py` | 签名（HMAC-SHA256，纯函数可单测）/ 代理优先直连兜底 / 无 key fail-safe / **两腿配对纯函数** / 下单函数（**默认拒发**） |
| `common/config.py` | 新增三个密钥字段与 `BITGET_TRADE_ENABLED`；**修掉一个泄漏洞**见 5.3 |
| `server/app.py` | 新增只读接口 `/api/account`（60 秒缓存） |
| `web/` | 新增页签 **「⑤ 我的账户」**：账户总览 / 持仓表 / **待处理（只成交一条腿）** / 未接入时的三步指引 |

**两腿配对**（用户提的做法）落成 `pair_legs()` 这个**纯函数**，四种形态：

| 形态 | 含义 |
|---|---|
| `both` | 两条腿都在 -> 对冲完好 |
| `spot_only` | 只有现货腿 -> **裸多敞口（危险）** |
| `perp_only` | 只有永续腿 -> **裸空敞口（危险）** |
| `flat` | 两条腿都没有 -> 空仓 |

配对正确性用**合成样本**单测（不联网、不需要 key）：现货 `available + frozen` 相加、
空头记为负、极小零头不误报、动作只能由状态反推。

### 5.2 本轮**有意未实现**的部分

`place_order()` 在 `BITGET_TRADE_ENABLED=off`（默认）时**直接返回"未启用"**，
即使 key 带交易权限也走不到发送那一步。**最后那行"真正发送"留到：**

1. `--probe` 用真 key 把接口路径验证过；
2. 7 道护栏逐条落地并有自检；
3. 用户明确开启 `BITGET_TRADE_ENABLED=on`。

### 5.3 顺带修掉一个**密钥泄漏洞**（加字段之前必须先堵）

`common/config.py` 的打码逻辑原本是 `if "KEY" in name` —— 而
`BITGET_API_SECRET` / `BITGET_API_PASSPHRASE` **都不含 "KEY"**，
一旦加上这类字段，`--check` 与 `--json` 会把密钥**明文打印**。
已改为 `is_secret_name()`（KEY / SECRET / PASSPHRASE / TOKEN / PASSWORD / PRIVATE），
并写进自检特征。实测造两个假密钥验证：`describe()` 输出里**不再出现明文**。

### 5.4 诚实声明：接口路径**尚未用真 key 验证**

Bitget 文档站是 JS 渲染的，本机 `web_fetch` 抓不到正文（实测失败）。
所以 `ENDPOINTS` 里的路径来自公开文档的**页面标题**与通行用法，**没有真 key 跑通过**。
因此：

- 路径与参数名**集中在 `ENDPOINTS` / `PARAMS` 一处**，改只改一处；
- 提供 `python common/bitget_private.py --probe`，逐条调用并打印 API 的**原始返回**；
- 模块自报 `VERIFIED_WITH_REAL_KEY = False`，页面据此**如实显示"未验证"**，
  并提示"在变成已验证之前以交易所 App 为准"；
- **探不通就报不可用，绝不编一个仓位出来。**

这对应用户的安全诉求：**宁可显示"看不到"，也不显示一个假的持仓。**

### 5.5 你接下来要做的三步

1. 在 Bitget 创建 API Key，权限勾**只读**先跑一遍（确认接口通）；
2. 三个值写进本机 `.env`（**别贴聊天里**）；
3. `python common/bitget_private.py --probe` —— 逐条验证并把原始返回打出来。
   我会按 probe 的结果把 `ENDPOINTS` 校准，然后才谈「补腿」按钮的最后一步。
