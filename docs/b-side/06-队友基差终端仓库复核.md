## 二、五处必须统一或修正的口径

### 2.1 基差符号：甲侧是**倒数口径**，与乙侧已定口径相反（必改）

| 口径 | 定义 | 20:45 快照 TSLA | 出处 |
|---|---|---|---|
| **甲侧（现行）** | `(现货/永续 − 1) × 10000` | **−27.20** | `build_panel.py:176`、`00/04/05/06` 全部文档 |
| **乙侧（已定，标准期货口径）** | `(永续/现货 − 1) × 10000` | **+27.27** | 本工作台 `README` §五、`04-本机复核与勘误.md` |

**复算证据**：1h 面板按甲侧口径复算**0 行不符**，按乙侧口径**13,586 行不符** → 甲侧口径确认无误（是两种约定，不是算错）。
**影响**：两方所有已写下的数字符号相反；`±` 一错，**成本模型的加减方向与下单方向（多现货/空永续）全跟着错**——这正是他自己登记的 **K10 风险**。
**建议动作**：① 口径统一为 **`basis_bp = (P_perp / P_spot − 1) × 10000`，正 = 永续溢价**（与期货教科书、与"basis = 期货 − 现货"一致）；② 甲侧 `build_panel.py` 改一行（或加常量 `BASIS_SIGN = −1` 并在报告显式声明）；③ 已发布的 `00/01/03/04/06` 里所有基差数字**翻号重写**，并保留一句"本轮已统一口径，此前文档为倒数口径"。
**DRI**：甲侧（改代码 + 改他自己的文档）｜乙侧（改本工作台 `README`/`04`）。

### 2.2 面板对齐：`--max-gap 3` 在**日线**上等于允许"拿 3 天前的现货价配今天的永续价"（必改）

`build_panel.py` 默认 `--max-gap 3`（单位 = bar 数）：1min 档=3 分钟（可接受），但**1day 档=3 天**。实测后果：

| 面板 | 滞后=0 | 滞后>0 | 结论 |
|---|---|---|---|
| 1h（10 配对） | n=12,711，sd **20.65** | n=925，sd **51.94**（2.5×） | 极端值（±286bp）**全部**来自滞后>0 |
| 1day（213 配对） | n=19,922，sd **91.65** | n=3,026，sd **162.21**（1.8×） | \|基差\|>300bp 的 341 行里 **52.5% 是滞后>0**（全样本仅 13.2%） |

**机制**：现货（rToken）零成交分钟不上线，**日线也有 13.2% 的行缺当日 bar**；一旦落到"前一天/前两天"的现货收盘价，算出来的"基差"里就混进了**标的当天的涨跌幅**（量级 ±100~300bp），而真信号只有 ~10bp → **污染比信号大一个量级**。
**建议动作**：`--max-gap 0`（至少日线必须为 0）；`lag>0` 一律记缺测；重跑两张面板。
**副作用（必须同步改口径）**：剔除滞后>0 后，**日线的"休市 vs 盘中"差从 3.4bp 缩到 1.0bp**（−8.13 vs −7.08）→ "休市时段基差更负"这句话**方向仍成立、幅度必须下调**。
**注意**：1h 面板结论**稳健**——剔除后四个时段中位几乎不动（closed −12.46 → −12.35），可以继续用。
**DRI**：甲侧（改 `build_panel.py` + 重跑）。

### 2.3 日线面板的 `closed` 标签 ≠ 休市，而是"周六/周日那一根"（必改表述）

复算：日线面板 **23,330 行的 `ts` 全部是 `16:00Z`**（= 北京次日 00:00，Bitget 日线按 UTC+8 切），而 `closed` 行 **100% 是周六（3,148）+ 周日（3,157）**。
→ 日线 bar 一根覆盖整个北京日，**同时包含美股盘中与收盘后**；`session_of()` 只按 bar 的**开盘时刻**打标签，于是：**工作日夜间休市被并进 `intraday`，`closed` 只剩周末**。
**影响**：报告里"休市 n=6,305 / 盘中 n=16,643"的对比，真实含义是 **"周末 bar vs 工作日 bar"**；两个大时段被混在一起，会**低估**休市效应（方向上是保守的，但仍属表述错误，评委可一眼看穿）。
**建议动作**：① 时段结论**只用 1h 面板**（它的标签是正确的）；② 日线面板要么改列名 `weekend/weekday`，要么在表下注明"日线粒度无法区分盘中/夜间"。
**DRI**：甲侧。

### 2.5 mid 口径 ≠ 可成交口径：**收益的很大一块是"不付点差"**（必改闸门）

用他 171 轮盘口重算同一时点的三种"基差"（标准口径，正 = 永续溢价）：

| 口径 | 含义 | 全体中位 |
|---|---|---|
| `B_mid` | 中间价对中间价（研究口径，= 他面板的算法） | **+15.6 bp** |
| `B_taker` | 现货腿吃单（买 ask）+ 永续腿吃单（卖 bid） | **+12.1 bp** |
| `B_maker` | **现货腿挂 bid 成交**（maker）+ 永续腿吃单 | **+20.5 bp** |

**扣费后的净边际（中位）**：

| 情景 | 现货maker | mid |
|---|---|---|
| 现货 **taker** 10bp + 永续 taker 6bp | +4.5 bp | **−0.4 bp** |
| 现货 **maker** 8bp + 永续 taker 6bp | +6.5 bp | +1.6 bp |
| 现货 maker 2bp + 永续 taker 6bp | +12.5 bp | +7.6 bp |
| 现货 **0 费** + 永续 maker 2bp | +18.5 bp | +13.6 bp |

**三条硬话**：
1. **现货腿一旦吃单，中位基差就被手续费吃光（−0.4bp）** → 策略要么做 maker，要么只在极值区（P95 = +27.6bp）入场；
2. `B_maker − B_mid ≈ +5bp` ≈ **半个现货点差**（当日 10 个标的中位 10.9bp）→ "maker 赚点差"这句话在数量上就是这么来的，**它同时也是逆向选择的暴露面**（F6/F7 的核心）；
3. 点差越宽的标的**未必**基差越大：`MRVL` 现货点差 45.63bp（全池最宽）但中位基差只有 +8.45bp，**吃单后倒亏 15bp**；反例是 `GOOGL/META/NVDA`（点差 8–14bp、基差 22–24bp）。→ **闸门必须逐标的、用可成交价算，不能用全池中位数。**
**建议动作**：F5 闸门改口径为"可成交基差 − 实际费率 > 安全边际"，并把 `B_mid / B_maker / B_taker` 三列一起写进面板。
**DRI**：乙侧（策略层）。

## 四、⚠️ 采样器不止一个写入者（需甲侧今晚核实）

**证据**（`data/spread/2026-09-12.csv`，171 轮 / 3,420 行，轮间隔分布）：

```
轮间隔(秒): (43.6, 40次) (16.5, 40次) (16.4, 35次) (43.5, 22次) (40.1, 13次) (3.4, 13次)
```

1. **密度是设定值的 2.1 倍**：60 秒节奏跑 80.5 分钟应得约 81 轮，实测 **171 轮**；
2. **间隔成"互补对"**：16.5 + 43.6 = 60.1 → 典型的**两个 60 秒循环、相位相差 16.5 秒**；
3. **出现 3.4 秒间隔**：单进程固定节奏（`sleep(interval − 耗时)`，若耗时>interval 则间隔=耗时）**不可能**产生 3.4 秒——除非写入者是两个。
4. 全池文件同病：63 轮里 **23 轮与其相邻轮相差 < 50 毫秒**。

**为什么他的自检没发现**：他去重用的键是 `(ts_ms, symbol, venue)` 完全相等——**两个进程各自打自己的毫秒时间戳，天然不会重复**，所以"0 重复"这个结论是**假阴性**。
**影响**：数值不受污染（追加写、无截断），但**轮次/样本量虚高一倍**，"覆盖率 99.7%"这类基于轮数的说法要改用墙钟时间重算；两个进程同时追加同一文件也存在极端情况下的行交错风险。
**建议**：① 用"每轮行数是否恰好等于配对数×2 + **每分钟轮数是否 ≈ 1**"或"轮间隔是否成互补对"来检测；② 确认只有一个实例在跑（他自己的终端 + 沙箱会话各起过一个是最可能的原因）；③ 长期常驻**只留一个**，并在采样器启动时打印 PID 到心跳（已有）。
**DRI**：甲侧。

## 八、追加发现（09-13 00:20 补充，非阻塞）

### 8.1 `base` 字段的派生 bug

**现象**：你的 `data/spread/2026-09-12.csv` 里 `HOOD` 的 `base` 写成了 **`HOO`**（而 `universe.csv` 里是正确的 `HOOD`）。

**根因**：`spread_sampler.py:236`（`:285` 同款）

```python
rec["symbol"].rstrip("USDT").lstrip("R")
```

`str.rstrip("USDT")` 的参数是**字符集**，不是后缀——它会从右往左**逐个**剥掉属于 `{U,S,D,T}` 的字符，剥到不属于为止：

| symbol | `rstrip("USDT")` 实际得到 | 应为 |
|---|---|---|
| `HOODUSDT` | **`HOO`** ❌ | `HOOD` |
| `MSFTUSDT` | **`MSF`** ❌ | `MSFT` |
| `AAPLUSDT` | `AAPL` ✅ | `AAPL` |

`lstrip("R")` 同理是字符集剥离（对 `RIO`、`ROK`、`RAM` 这类以 R 开头的真实代码有误剥风险），
只是本次 10 配对没踩到。

**影响**：本次仅 `HOOD` 一个配对受影响（10 个里 1 个），**分组功能不受影响**（同一 base 内部自洽）；
但**一旦按 `base` 与原生股代码或 `universe.csv` 做 join，会静默失配**（`HOO` 谁都不匹配，不报错）。

**改法**：

```python
sym = rec["symbol"]
base = sym[:-4] if sym.endswith("USDT") else sym     # 精确去后缀
base = base[1:] if base.startswith("R") else base     # 或用 universe.csv 的 spot_symbol→base 映射
```

更稳的是**别从 symbol 反推 base**，直接用配对配置里已有的 base 字段。

### 8.2 `_pid_alive()` 在 Windows 上会把启动打崩（残留锁 → WinError 87）

**现象**：锁文件残留（上次进程被强杀）时，重启**直接抛异常退出**：

```
File "...\spread_sampler.py", line 198, in _pid_alive
    os.kill(pid, 0)
OSError: [WinError 87] 参数错误
```

**根因**：`os.kill(pid, 0)` 在 Windows 上**不是**可靠的"进程存活探测"——
CPython 会 `OpenProcess(PROCESS_ALL_ACCESS, ...)`，pid 已不存在时 `GetLastError() = ERROR_INVALID_PARAMETER(87)`
→ 抛 `OSError`。而锁文件里存的是**上一次启动的 pid**，进程被强杀后锁不会自动消失
（`release_lock()` 只在正常退出时执行）。

**影响**：**残留锁把下一次启动挡死**，且给出的是 traceback 而不是可读提示 → 只能手动删锁文件才能恢复
（乙侧 09-12 23:38 实际踩到）。

**建议改法**（乙侧本机副本已打此补丁）：

```python
def _pid_alive(pid):
    if pid <= 0:
        return False
    try:
        os.kill(pid, 0)
        return True
    except Exception:          # WinError 87 / 5 / 任何异常，一律视为「不存活」
        return False
```

并把锁分支整体包一层 `try`：**锁检测一旦失败，按无主锁接管**——
双写风险交给「每分钟轮数 ≈ 1」这个自检兜底，也好过脚本完全起不来。

**更彻底的方案**（可选）：别用 pid 探测，改成**独占打开锁文件**（`fd = open(LOCKFILE, "x")`
或 Windows 下 `msvcrt.locking()`）——进程死亡时文件句柄由 OS 自动释放，这是 Windows 上最可靠的单实例做法。

**乙侧处置**：本机运行副本已按上面第一段改好（`except Exception` + 锁分支兜底），
行为与原件的差异仅此一处，其余逻辑一字未改。
