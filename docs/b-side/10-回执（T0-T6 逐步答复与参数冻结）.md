### 2.1 哈希口径：行尾无关（推送前我自查揪出的一处硬伤，已修）

`frozen.json` 的 SHA256 是**文本归一化后**的内容哈希：哈希前把 CRLF 全部换成 LF；
二进制文件仍取原始字节。每条另记一个 `eol` 字段，**仅供参考，不参与比对**。

**为什么非改不可**：本仓库 `core.autocrlf=true`，且**没有 `.gitattributes`**。同一个 blob
在不同平台 / 不同设置下 checkout 出的工作区字节不同 —— Windows 默认 CRLF，Linux 与
`autocrlf=false` 是 LF。若直接哈希磁盘原始字节，会有两层假报警：

1. 你在 **Linux 或 `autocrlf=false`** 下 clone → 22 个 A 侧文件会**全部**报「SHA256 变了」；
2. 更近的一层：本机实测有 **6 个**文件当前恰好是 LF（三个滚动/回测 CSV、
   `tools/b_side_backtest_basis_timing.py`、`tools/b_side_backtest_fee_sensitivity.py`、
   `tools/b_side_rolling_sharpe_plot.py`）。`autocrlf=true` 会在 checkout 时把它们翻成 CRLF
   —— 也就是**你在自己 Windows 上干净 clone 一次，这 6 个就会误报**。

结论：不归一化的话，这份「冻结」在**任何一次干净 clone 之后都自动失效**，硬门禁等于纸糊。

**已做的验证**：35 个被冻文件在「原始 / 全 CRLF / 全 LF」三种形态下哈希完全相同，
`--verify` 仍报 **35 一致 / 0 不符 / 0 新增**。

**你那边怎么复核**：clone 后直接跑
`python tools/freeze_params.py --repo . --verify`，应得 `35 一致 / 0 不符 / 0 新增`，
与你的 `autocrlf` 设置、操作系统无关；若某文件出现 `[i] 工作区行尾不同` 只是提示，不影响结论。
