## 1. 这是什么（一句话）

> 给定**当前盘口**和**我想要的仓位**，这笔单应该**吃单**还是**挂单**？**挂在哪个价**？**分几笔**？

—— 这是一个真实的、可量化的执行决策问题。它的输入全部来自项目一已经采到/算出的数据，
**不需要新采任何数据，不需要任何 API Key**（除可选的事件过滤外）。

## 2. 为什么这是独立的项目（而不是项目一的附录）

| | 项目一（Alpha Factory） | 项目二（Execution-aware Alpha） |
|---|---|---|
| 回答的问题 | **在哪里**有可捕获的价差 | **怎么执行**才能把它拿到手 |
| 核心变量 | 基差 `B`、时段 `route/session` | 点差、深度、成交概率、逆向选择 |
| 输出 | 策略定义与门槛（11.34 bp） | **逐单执行建议**（吃/挂/挂哪/分几笔） |
| 用户 | 想做价差的研究者 | **任何要下单的人**（执行成本是普适痛点） |
| 大模型角色 | 开发期为主 | **运行期**：事件风险判断（见 §4） |

**关键**：项目一的净收益判据反复撞到同一堵墙 ——
`docs/14` 实测现货腿**成交率 0.5%–86.5%（与点差宽度反向）**、
**逆向选择 −0.21 ~ −21.84 bp**。
**项目一能算出"能不能赚"，但算不出"这一单该怎么下"。** 那正是项目二填的空。

## 3. 现状：核心模型（`execution_cost.py`）

**确定性部分，已可运行。** 输入的每一个参数都标注了来源与实测值：

```
吃单成本 = 半幅点差 + 手续费 + 冲击(吃穿 N 档)
挂单成本 = 手续费 − 半幅点差(成交才赚) + P(不成交)×错过成本 + 逆向选择期望
建议     = argmin(成本)，并给出"挂单价 → 成交概率 → 期望成本"曲线
```

## 4. 大模型（LLM）在项目二里的角色 —— **运行期，不是装饰**

这是本项目与项目一最大的结构差异，也是表单「大模型在项目中的作用」的**真正答案**。

**LLM 做的事：事件风险判断。**
挂单的本质是"我愿意在这个价位等"；但如果**此刻正在发生信息事件**
（财报、宏观数据、突发新闻），那么"等到成交"往往意味着
**对手方知道你不知道的事** —— 这正是 `docs/14` 实测的**逆向选择**。

| 环节 | 谁做 | 为什么不能互换 |
|---|---|---|
| 点差/深度/手续费/资金费 | **确定性代码** | 数值计算，LLM 只会引入噪声 |
| 成交概率、期望成本、最优挂价 | **确定性代码** | 同上，且必须可复现、可审计 |
| **"现在是不是有信息事件？"** | **LLM** | 输入是**非结构化**的（新闻、公告、财报日历），规则写不全 |
| 事件 → 执行建议的映射 | 确定性规则 | "事件窗口内禁止挂单"是硬规则，不该让 LLM 自由发挥 |

**设计原则**：LLM 只输出**结构化判断**（`{is_event_window, severity, reason, confidence}`），
**决策权仍在确定性代码里**。LLM 拿不到"下单"的权限，也不能推翻硬规则。
—— 这样既能说清 LLM 的作用，又不会让系统变成不可复现的黑盒。

`event_gate.py` 实现三种模式：
- `static`：只用手工/抓取的财报日历（**无 LLM 也能跑**，这是回退路径）
- `llm`：接一个 OpenAI 兼容端点做新闻分类（需要用户配置 key）
- `auto`：有 key 用 llm，没有就用 static —— **绝不因为没有 key 就崩**
