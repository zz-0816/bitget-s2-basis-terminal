## 3. 现状：核心模型（`execution_cost.py`）

**确定性部分，已可运行。** 输入的每一个参数都标注了来源与实测值：

```
吃单成本 = 半幅点差 + 手续费 + 冲击(吃穿 N 档)
挂单成本 = 手续费 − 半幅点差(成交才赚) + P(不成交)×错过成本 + 逆向选择期望
建议     = argmin(成本)，并给出"挂单价 → 成交概率 → 期望成本"曲线
```

### 3.1 ⭐ 双腿成交概率 = **实测联合分布**（2026-09-18 修正一个口径错误）

双腿模型的关键概率是 `P(两腿都成交) / P(只成交一腿) / P(都没成交)`。
它过去写成 `p_s × p_p`，标为"独立近似"—— 但**真正的问题是分母搞错了**：

| | 旧口径 | 现在 |
|---|---|---|
| 分母 | **成交笔数**（"每笔成交里有多少笔打到我们的价"） | **挂单次数**（一个 30 秒盘口区间 = 一次挂单机会） |
| 回答 | 有人交易时我们被成交的概率 | 我们挂上去会不会被成交 |

两个 per-trade 概率**不能相乘**：乘出来的既不是挂单成交概率、也不是条件成交概率。
实测（`tools/joint_fill_analysis.py`，9 个标的、50,081 个窗口）：

| 概率 | 实测（合并） |
|---|---|
| P(两腿都成交) | **0.70%** |
| **P(只成交一腿)** | **24.9%** ← 单腿裸露才是主要风险形态 |
| P(都没成交) | 74.4% |
| 两腿相关 | phi **+0.031**（弱正相关；来自"两边同时活跃"这一层） |

旧口径把 `META` 的 `P(两腿都成交)` 算成 **29.2%**，实测只有 **2.37%**（高估 12 倍）；
`GOOGL` 高估 18 倍。影响对照见 `python tools\joint_fill_check.py`：
**3/9 个标的最优执行方式改变**（旧口径偏向"现货挂单+永续吃单"，实测下
`stockroute` 时段现货腿成交率≈0，那条路径实际上是死的）。

⚠️ **覆盖限制**：现货成交带**只到 2026-09-14**（之后 0 笔），
所以联合分布只能在那三天测；模型按 route 取分层值，取不到就回退独立近似
**并在返回体里标注 `joint_source`**。完整口径见 `docs/14` §9。

## 4. 大模型（LLM）在项目二里的角色 —— **运行期，不是装饰**

这是本项目与项目一最大的结构差异，也是表单「大模型在项目中的作用」的**真正答案**。

**LLM 做的事：事件风险判断。**
挂单的本质是"我愿意在这个价位等"；但如果**此刻正在发生信息事件**
（财报、宏观数据、突发新闻），那么"等到成交"往往意味着
**对手方知道你不知道的事** —— 这正是 `docs/14` 实测的**逆向选择**。

| 环节 | 谁做 | 为什么不能互换 |
|---|---|---|
| 点差/深度/手续费/资金费 | **确定性代码** | 数值计算，LLM 只会引入噪声 |
| 成交概率、期望成本、最优挂价 | **确定性代码** | 同上，且必须可复现、可审计 |
| **"现在是不是有信息事件？"** | **LLM** | 输入是**非结构化**的（新闻、公告、财报日历），规则写不全 |
| 事件 → 执行建议的映射 | 确定性规则 | "事件窗口内禁止挂单"是硬规则，不该让 LLM 自由发挥 |

**设计原则**：LLM 只输出**结构化判断**（`{is_event_window, severity, reason, confidence}`），
**决策权仍在确定性代码里**。LLM 拿不到"下单"的权限，也不能推翻硬规则。
—— 这样既能说清 LLM 的作用，又不会让系统变成不可复现的黑盒。

> 多 Agent 团队（§5）在这条原则上**没有例外**：分析师、辩论、交易员、风控官
> 四层全部是确定性代码，**LLM 仍然是唯一的一个点**（事件判断）。
> 这不是"没用上模型"，而是刻意为之 —— 见 §5 的单调性约束。

`event_gate.py` 实现三种模式：
- `static`：只用手工/抓取的财报日历（**无 LLM 也能跑**，这是回退路径）
- `llm`：接一个 OpenAI 兼容端点做新闻分类（需要用户配置 key）
- `auto`：有 key 用 llm，没有就用 static —— **绝不因为没有 key 就崩**

### 4.1 ⭐ 已联动：挂单前先问闸门（`--two-leg` 默认开启）

**闸门是否决权，不是建议。** 执行成本模型在推荐任何**挂单类**方案前都会先问闸门：

| 闸门判定 | 对执行方案的影响 |
|---|---|
| `none` | 三种方案（全挂单 / 现货挂单+永续吃单 / 全吃单）**都保留** |
| `caution` | 保留，但输出里标注「可挂但需缩小规模 / 放宽价位」 |
| **`block`** | 🔴 **两个挂单类方案直接作废** —— 只剩「双腿全吃单」；若其成本不可接受，就**不做** |
| 闸门**不可用** | ⚠️ 降级为 `caution` 并明确标注 —— **绝不当作「没有事件」** |

**为什么必须联动**：挂单的收益来自"等到成交"，而事件窗口里"等到成交"
往往等于**被逆向选择**（`docs/14` 实测 −0.21~−21.84 bp；
`docs/TASKS.md` 已记一个实测案例：7/23 某标的 −7.65% → 实际 −8.83%，
**是财报，不是错价**）。

**注意闸门不改变吃单方案的成本** —— 吃单是立即成交，
不承担"在事件里等"的风险。所以否决的只是挂单，不是整个交易。

自检覆盖**否决路径**本身（只测"允许"路径等于没验证门起作用）：
```powershell
python project2\execution_cost.py --selftest
# 6 项：放行 / 否决 / 否决后只剩全吃单 / 两个挂单方案都被剔除 /
#       闸门不可用降级为 caution / --no-gate 显式标注
```

## 5. 多 Agent 团队（`agent_team.py`）—— 四层，全部确定性

设计依据 `docs/25`；分工参考"分析师 → 研究员辩论 → 决策团队风控执行"。

> ⚠️ **必须先说清的一件事**：这四层里**没有一层是"让 LLM 再写一段话"**。
> LLM 的唯一职责仍是「现在是不是有信息事件」（`event_gate`），
> 其余全部是**确定性代码**。理由见 `docs/25` §2.2：agent 决定"这一单做不做"，
> **不决定"门槛是多少"** —— 否则报告里的数字无法复跑。

| 层 | 做什么 | 铁律（结构上防住失败模式） |
|---|---|---|
| ① 分析师（**5 路**） | basis / sentiment / news / technical / **execution_risk** **各自独立**取数 | **没有引用已实测的量的结论一律作废** |
| ② 多空辩论 | 多头 vs 空头立论 → 交叉质证 → 确定性裁决 | **给不出证伪条件的论点一律作废**；同一证伪条件不得重复计分（防"一个判断换三个说法"）；方向自相矛盾的论据扣分 |
| ③ 交易员 | 把「做不做」翻译成**可执行订单**：方式 / 规模 / 价位 / 拆几笔 | 不新造阈值：规模 = min(请求, 可捕获名义额, 首档深度×25%) |
| ④ 风控官 | **一票否决** + 缩规模 + 强制吃单；含 agent 提出的假设 | 每条规则都要回答：引用哪个实测量 / 触发后做什么 / 什么条件下撤销 —— **未触发的规则也留痕** |

### 5.0 🔴 哪些是 agent 做的，哪些必须是代码（最多人问的一条）

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 5 路独立分析（含**执行风险评估**） | **agent** | 需要把跨表事实联系起来 —— 例如"现货报价在动、但 4 天没有成交"。规则写不全 |
| 多空立论、交叉质证、**提出风险假设** | **agent** | 这是"发现与论证"：它产出假设 + 实测量 + 阈值 + **证伪条件** |
| 事件判断（有没有信息事件） | **LLM**（运行期唯一职责） | 输入是非结构化新闻；**没有 key 就退化为确定性日历，并如实标注"本次未使用 LLM"** |
| 成本数字、最优执行方式 | **确定性代码** | 数值计算；LLM/agent 只会引入噪声 |
| **一票否决、最终规模、最终立场** | **确定性代码** | 门槛与规模必须**可复跑**（`--replay` 会逐字节比对）；否则报告里的数字无法验证 |

**分界线一句话**：**agent 负责「发现与论证」，代码负责「执行与守边界」。**
agent 提出的风险假设会被风控官当作规则执行（日志里以 `agent:` 前缀标识），
但**仍然只能收紧**，且整个决策可用 `--replay` 复跑。

> 实测（2026-09-18）：`execution_risk` 分析师提出 2 条假设
> （`agent:leg_risk`、`agent:stale_quotes`），其中 `agent:stale_quotes`
> 因"现货腿 6679 分钟无成交"**真的触发了一票否决**（`agent_driven: true`）。
> 自检里有一条专门验证"agent 的假设确实能改变决策"，以及
> "没有假设时不产生 agent 规则"（防它变成万能借口）。

### 5.1 🔴 单调性：交易员与风控官**只能收紧，不能放松**

这条是「一票否决」能不能算数的分界线。立场序 `proceed(2) > caution(1) > stand_down(0)`，
最终立场必须 ≤ 辩论立场，最终规模必须 ≤ 交易员规模 ≤ 风控规模上限。
自检用 **3 立场 × 3 闸门状态 = 9 组**穷举验证，并单独验证"想放松会被夹住"。

风控官规则表（`risk_officer()`，顺序固定 → 确定性）：

| 规则 | 级别 | 触发条件（全部是已实测的量） | 处置 |
|---|---|---|---|
| `gate_block` | 否决 | 事件闸门 severity = `block` | 不开新仓 |
| `debate_stand_down` | 否决 | 辩论裁决 = `stand_down` | 不开新仓 |
| `cost_exceeds_edge` | 否决 | 最优执行成本 **> 11.34 bp**（`docs/14` 门槛）**且**毛边际 < 该门槛 | 不开新仓 |
| `adverse_selection` | 否决 | 现货腿 f_dmid ≤ **−3.0 bp**（挂单被系统性挑选） | 不开新仓 |
| `thin_capacity` | 警示 | 可捕获名义额 < 1,000 USD | 规模收到 10% |
| `thin_depth` | 警示 | 单笔 > 首档深度 × 25% | 规模收到 25% 首档 |
| `leg_risk_high` | 警示 | P(只成交一腿) > 50% | 强制「双腿全吃单」 |
| `no_capacity_data` | 警示 | 容量数据缺失 | 不开新仓（**数据缺失 ≠ 没有风险**） |
| `no_cost_data` | 警示 | 成本数据缺失 | 不开新仓（无法定价的单不许下） |

> **提醒强度（用户 2026-09-20 定）**：每条规则与风控结论额外带一个统一强度
> `intensity` —— `veto` → 🔴 **红**、`caution` → 🟡 **黄**；**未触发的规则不带等级**
> （**没有绿**：没有提醒就不占色位）。映射写在 `common/alert_level.py`，
> 与持仓期巡检 `tools/position_watch.py`（`critical` → 红、`warn` → 黄）**共用同一份实现**。
> ⚠️ `intensity` 只是**展示层**字段，不参与否决/缩规模。

**为什么成本否决条是"成本越线 **且** 毛边际不足"、而不是只凭毛边际**：
毛边际（basis 净收益 + 资金费）是**项目一的策略结论**，只凭它下结论就等于
风控官替研究层拍板了；加上"成本这一侧"，否决才完全建立在**执行层**的事实上。
两侧用的是**同一个已实测阈值**（11.34 bp），不新造数字。

**名义额下限 100 USD**：规模被压到没有意义的量级时，正确结论是"不做"，
而不是"用 73 USD 去做一笔套利"。触发时最终规模归零，并在 `final.why` 里
明写"是哪一级把它压下来的"（`min_notional_binding` 字段可查）。

| ③ 交易员 | 方式 / 规模 / 拆单 / 价位 / 三方案成本 / 规模上界及其三个来源 |
| ④ 风控官 | **9 条规则逐条留痕**（含未触发的 measured 与撤销条件） |
| ⑤ 决策 | 各阶段 stance 与规模轨迹、单调性检查、`decision_hash` |

### 6.1 `--replay` 怎么判"可复现"（把话说死，而不是含糊说"通过"）

日志哈希覆盖了**生成时间与输入文件指纹**，所以复跑必然会得到不同的哈希 ——
这不是失败。判定因此分成两类：

| 类别 | 字段 | 要求 |
|---|---|---|
| **契约字段** | 参数 / 规则表 / 最终立场 / 最终规模 / 订单方式 / 风控降级路径 / 单调性 | **必须逐字节一致**，否则 `--replay` 退出码 1 |
| **实时量** | 盘口快照、点差、成本、各规则实测值 | 允许漂移（采样器在持续写入），但必须**如实列出** |

另外还有一道**诚信校验**：日志内容重新算哈希，与它自己记录的 `decision_hash` 比。
自检里用"篡改 `final_qty_usd`""删掉一条风控规则"两个用例验证它真的抓得住 ——
实测踩到过：没有这一步时，"记录哈希"和"复跑哈希"可能拿的是同一个**没重算过**的字段，
于是被改过的日志照样显示"一致"。

日志的**输入清单**里包含成本标定所依赖的全部文件，其中就有
`joint_fill_all*.csv` —— 改了标定，日志哈希随之改变，复跑就会报不一致。

### 6.2 合成场景（`--scenario`）—— 演示用，**不是实测**

盘口是实时采样的，某些时段（比如现在）现货首档只有几百美元，
任何规模的单都会被"深度约束"压到名义额下限以下 —— 这是**真实结论**，
但也就看不到"能下单"那条路径长什么样。所以留了三个**明确标注为合成**的场景：

```powershell
python project2\agent_team.py --base NVDA --scenario viable --trader --log
python project2\agent_team.py --base NVDA --scenario blocked --trader
python project2\agent_team.py --base NVDA --scenario thin    --trader
```

- `viable`：假想盘口深度充足、往返成本为负（挂单赚点差）→ 走完到「谨慎执行 + 5000 USD 订单」
- `blocked`：假想事件窗口 → 闸门 block，两个挂单方案作废，只剩全吃单
- `thin`：本轮真实账面成本 + 薄盘口 → 复现「被压到名义额下限」这条路径

🔴 防误引用的三重保险：日志里 `parameters.synthetic = true` 与场景说明；
文件名带 `-synthetic-<场景>`（**绝不与实测日志重名**）；合成场景**不把**
orderbook 写进输入清单（因为确实没读盘口）。分析师与辩论两层仍走**真实数据**。

## 7. 与项目一的关系（单向只读）

```
project2/  ──只读──>  data/spread/*        （实时盘口）
           ──只读──>  data/derived/*       （成本参数、摩擦预算、资金费）
           ──只读──>  common/market_calendar（口径：session / route）
```

**反向为零**：项目一**不依赖**项目二。项目一可以选择性地引用项目二的执行建议
（那是加分），但即使项目二整个删掉，项目一也必须能独立跑通 ——
这是"两投须为独立项目"的硬要求。
